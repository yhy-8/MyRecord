# AgentRecord 运行机制与数据

本文说明程序怎样读写文件、维护 SQLite、执行自动任务、处理故障并完成 Linux 部署。产品原则和模块边界见[设计原则与系统架构](./设计原则与系统架构.md)，模型阶段的详细协作见[Agent 与报告流程](./Agent与报告流程.md)。

## 1. 启动、配置与路径

源码运行入口是根目录 `main.py`，也可以通过 `python -m AgentRecord` 启动。`settings.py` 从应用目录读取 `config.yaml`，所有相对数据目录都以配置文件所在目录为基准，而不是以当前终端目录为基准。

主要配置分为三类：

- `current_model` 和 `models`：选择日记总结与四个报告 Agent 共用的模型配置。
- `third_search`：周报固定搜索的接口、密钥、结果数和超时；月报不使用。
- `automation`：总开关以及日记总结、周报、月报各任务开关。

模型配置中的 `model_id` 是真正发给接口并显示在报告中的模型。`json_mode` 控制正式 Agent 是否请求 JSON Output；`max_tokens` 是接口生成安全预算，不是期望报告长度；`temperature` 和 API 地址也会进入报告输入签名，影响阶段能否复用。

`/m` 只原子更新配置中的 `current_model`，不会建立配置版本号或数据库迁移记录。项目由个人使用，当前配置即唯一需要支持的配置格式。

## 2. 日记文件与写入边界

日记路径为 `Records/YYYY-MM-DD.md`。文件包含一个可替换的 `<summary>` 区域和按时间追加的记录，例如普通记录、带标签记录和日记引用。

所有日记修改集中在 `journal.py`：

- 新记录立即追加到当天文件。
- 日记总结只替换 `<summary>...</summary>`，不重写其他记录语义。
- `/d` 只删除今日最后一条可删除记录。
- `/ref` 创建指向另一篇日记的标准相对引用，不允许新引用指向报告。

这些操作共用 `.journal.lock`，避免终端记录、自动总结和其他进程同时改写同一文件。普通记录路径不经过模型、搜索、报告 SQLite 或自动任务状态，因此即使外部接口不可用也能继续记录。

读取显式引用时，程序解析并规范化目标路径，再确认它位于 `Records` 根目录内且是日期命名的 Markdown 文件。测试会覆盖目录穿越，不能仅依赖引用文本看起来像相对路径。

## 3. 报告输入怎样构造

`analysis/context.py` 根据锚点日期确定完整自然周或自然月，读取周期内实际存在的日记，并从提供给模型的原始正文中省略已有 `<summary>`，防止把同日派生摘要重复当成原始记录。

输入组成及当前安全边界如下：

| 输入 | 用途 | 边界 |
|---|---|---|
| 当前周期原始记录 | 周报和月报的主要事实源 | 总体 Agent 输入安全边界为 120000 字符 |
| 单个记录分块 | 超大回顾按原顺序处理 | 每块目标不超过 30000 字符 |
| 显式引用日记 | 补足用户明确引用的历史上下文 | 最多 10 个文件，单文件先取 12000 字符，总计 30000 字符 |
| 近期日记总结 | 提供周期前的连续背景 | 向前最多 30 天，总计 20000 字符 |
| 月报支撑周报 | 避免丢失当月已有整理 | 总计 30000 字符，单份最多 12000 字符 |
| 单条搜索资料 | 周报研究证据 | 结果数由配置控制且程序上限为 10，标题和摘要受输入边界约束 |

这些数字控制送入接口的不可信或可增长上下文，不限制最终报告应该写多长。超出边界的输入会按明确顺序分块或停止继续装入，不在模型输出后按字符数否定正文。

同一报告的输入快照会计算哈希。哈希覆盖周期材料和影响语义的配置签名；周报还覆盖第三方搜索配置。只有输入、周期、来源、模型和阶段都等价时，失败运行中的已完成阶段才可能复用。

## 4. 一次报告运行的生命周期

手动命令和自动任务最终都调用同一份报告生成逻辑：

1. 确定周期、手动或自动来源和目标路径。
2. 获取 `.report.lock`，阻止同一时刻另一个报告进程进入。
3. 构造输入、模型与搜索签名，在 SQLite 新建 `running` 运行。
4. 执行回顾、审查，以及周报特有的选题、固定搜索、研究和审查。
5. 每个可审计或可复用阶段写入 `agent_artifacts`。
6. 中控组装报告头、正文、来源索引和 Token 汇总。
7. 在目标目录写一个本次运行唯一的临时文件，再以原子替换交付正式文件。
8. 把 SQLite 运行标记为 `completed` 并记录报告路径。

任一阶段抛出错误时，中控尽力把运行标记为 `failed` 并保存简化后的错误信息。临时文件不会作为正式报告留下。

如果正式文件已经替换、但随后 SQLite 完成状态写入失败，程序会删除新文件或恢复替换前的旧文件。这一补偿保证“报告存在”和“运行已完成”不会因提交顺序产生一半成功的状态。

手动版与自动版路径不同，手动重跑不会覆盖自动归档，自动任务也不会把手动报告误认作自己的完成产物。

## 5. 锁与原子操作

| 机制 | 保护对象 | 行为 |
|---|---|---|
| `.journal.lock` | 日记追加、总结替换和删除 | 等待获取，保证日记写入串行 |
| `.report.lock` | 周报/月报生成与交付 | 非阻塞获取，已有报告任务时新任务直接提示忙碌 |
| `.automation.lock` | 一次自动调度循环 | 操作系统级互斥，避免 cron 短进程重叠 |
| 临时文件 + `replace` | 日记、报告、配置和自动任务状态 | 同目录写完整内容后原子替换目标 |
| SQLite `BEGIN IMMEDIATE` | 单次运行或 artifact 状态变更 | 使用短事务，避免模型调用期间持有数据库锁 |

锁文件本身残留不代表仍被占用；真正互斥由操作系统锁状态决定。诊断时不应看到一个旧锁文件就直接删除数据或判定死锁。

## 6. SQLite 的定位

数据库位于 `AnalysisReports/.analysis.sqlite3`，只保存报告运行状态、阶段结果和重试缓存。它不保存权威日记，也不是打开报告的前提。

连接统一启用：

- 外键约束 `foreign_keys=ON`。
- WAL 日志模式。
- 10 秒连接和 busy timeout。
- 每次写入使用独立连接和短 `BEGIN IMMEDIATE` 事务。

数据库只有两张业务表，不维护 schema 版本表，也不提供旧结构迁移。

### 6.1 `analysis_runs`

一行代表一次周报或月报尝试。

| 字段 | 含义 |
|---|---|
| `id` | 随机运行 ID，主键 |
| `kind` | `weekly` 或 `monthly` |
| `period_start`、`period_end` | 报告覆盖的确定日期范围 |
| `origin` | `manual` 或 `auto`，同时决定目标文件后缀 |
| `trigger` | `manual`、`scheduled` 或 `retry` |
| `model_name` | 本次运行实际选择的模型标识 |
| `status` | `running`、`completed` 或 `failed` |
| `input_hash` | 周期输入和相关配置的内容签名 |
| `report_path` | 完成运行的正式报告路径 |
| `error` | 失败运行的简化错误信息 |
| `created_at`、`completed_at` | 启动和结束时间 |

索引 `(kind, period_start, period_end, origin, status)` 用于按报告周期和来源查找运行。

### 6.2 `agent_artifacts`

一行代表某次运行中的一个 Agent、搜索或控制阶段版本。

| 字段 | 含义 |
|---|---|
| `id` | artifact 随机主键 |
| `run_id` | 所属 `analysis_runs.id`，运行删除时级联删除 |
| `agent` | 阶段名称；记录到具体分块、记录组或主题 |
| `revision` | 同一运行、同一阶段的递增版本 |
| `status` | 该阶段是否完成或失败 |
| `payload_json` | 已解析响应、控制信息、证据或遥测组成的 JSON 载荷 |
| `error` | 阶段错误 |
| `created_at` | 保存时间 |

唯一约束 `(run_id, agent, revision)` 防止同一阶段版本重复写入。正文仍以最终 Markdown 报告为阅读载体，artifact 是审计与恢复材料。

### 6.3 Token 遥测

`AnalysisStore` 在内存中累计本次进程实际发生的模型调用：

- `prompt_tokens`
- `completion_tokens`
- `total_tokens`
- `cached_tokens`
- `cache_miss_tokens`

汇总值写入最终报告头。复用旧 artifact 时不把其历史 Token 再计入当前运行，因此报告展示的是本次实际接口消耗，而不是整条逻辑链曾经消耗过的总量。

### 6.4 阶段复用

报告失败后，重试可以查找等价失败运行中最新的 `completed` artifact。查询同时要求：

- 输入哈希相同。
- 报告类型、周期、手动或自动来源相同。
- 模型标识相同。
- Agent 阶段名称相同。

只有已经完成并经过当前程序验证的阶段可以复用。失败 artifact、不同模型、不同输入或不同来源不会混用。周报的搜索证据也受搜索配置签名约束。

### 6.5 无迁移策略

初始化时程序检查实际表集合和每张表的字段集合。只要结构与当前两表定义不完全一致，就停止并提示删除数据库，不尝试猜测或改写旧结构。

在确认没有报告进程运行后，可以删除：

```text
AnalysisReports/.analysis.sqlite3
AnalysisReports/.analysis.sqlite3-wal
AnalysisReports/.analysis.sqlite3-shm
```

下次报告运行会创建空数据库。已有日记和 Markdown 报告不受影响，但历史阶段缓存和运行审计会丢失。

## 7. 自动任务状态

自动任务状态保存在 `AnalysisReports/.automation-state.json`，采用临时文件原子替换。它与 SQLite 分工不同：SQLite 跟踪一次报告内部发生了什么，自动状态跟踪哪些日期或周期仍需运行、何时重试以及哪个前置任务正在阻塞。

主要状态包括：

| 状态 | 用途 |
|---|---|
| `pending_targets` | 每种任务等待处理的准确起止日期队列 |
| `errors` | 最近一次任务错误及时间 |
| `retry_after`、`retry_kind` | 下次允许重试的时间和故障类别 |
| `failure_counts`、`failure_keys` | 同一输入内容失败的次数和解锁签名 |
| `failure_targets` | 失败对应的原始日期或周期，避免跨日后漂移 |
| `current_task`、`current_task_detail`、`current_task_started_at` | `/status` 展示的当前工作 |
| `last_detection_hour` | 最近完成缺失扫描的小时水位 |
| `last_check_started_at`、`last_check_completed_at` | 最近调度进程的开始和结束时间 |

缺失目标先进入持久队列，再开始生成。因此即使进程中途退出、跨过午夜或后来被前置失败阻塞，任务仍指向最初发现的准确日期，不会悄悄改成“现在的上一天”。

## 8. 自动调度顺序

Linux 安装的 cron 每分钟启动一个短进程。进程取得 `.automation.lock` 后读取状态；同一小时只做一次新缺失检测，但每分钟都可以继续处理已到重试时间的队列。

任务顺序固定为：

```text
昨日日记总结 → 上一完整自然周周报 → 上一完整自然月月报
```

处理规则如下：

1. 每个新小时分别检查三个任务的默认目标，将缺失产物的准确目标入队。
2. 按上述顺序查看队首。日总结失败或尚未到重试时间时，周报和月报不会越过它。
3. 周报失败时月报等待；已经入队的月报目标不会丢失。
4. 成功或发现产物已存在后出队，再继续后续任务。
5. 正常 cron 每轮对每类任务最多消费一个队首目标；若前项成功，同一轮可以继续后续类别，但同类仍有更早目标时先结束本轮。
6. `/retry` 沿用相同依赖顺序，不提供绕过前置屏障的特殊捷径。

自动完成状态以真实产物判断：日记的 `<summary>` 是否已有内容，或对应 `_auto.md` 报告是否存在。手动报告不能替代自动报告完成标记。

## 9. 重试和故障分类

故障不会无限快速重跑：

| 故障 | 自动策略 |
|---|---|
| 连接、DNS、超时等网络问题 | 5 分钟后重试 |
| HTTP 429 限流 | 5 分钟后重试，由外层调度控制节奏 |
| 模型、密钥、接口或搜索配置错误 | 标记 `blocked`，等待配置变化或用户处理 |
| 内容、JSON、审查或其他非网络失败 | 首次失败后到下一整点再试一次 |
| 同一输入第二次内容失败 | 标记 `content_blocked`，不再自动循环 |

内容阻塞的签名覆盖对应日记输入、模型配置，以及周报的搜索配置。输入或配置改变后，签名改变，任务可以重新进入自动尝试；用户也可以使用 `/retry` 明确发起重试。

`ai_client.py` 自身只对适合在单次请求层解决的问题做有限重试：连接、超时、HTTP 408 和 5xx 最多尝试三次。429 留给自动任务按分钟调度；鉴权失败、资源不足、输出过滤和 `length` 截断会被明确分类。接口返回成功终止但最终正文为空时，客户端只补答一次。

## 10. 第三方搜索

周报必须有可审计的第三方搜索配置。每个 Planner 查询由中控固定调用一次，结果数量受配置和程序上限共同约束。程序规范化 URL、去重并保存搜索遥测。

搜索结果是外部不可信输入：

- 标题、摘要或网页文字不能覆盖系统提示词。
- 查询在发出前会清理邮箱、长数字、本地路径等敏感形态。
- Researcher 不接收真实链接；最终链接由中控从保存的结果渲染。
- 月报完全不调用第三方搜索，因此搜索接口故障只影响周报。

## 11. Linux 自动任务部署

安装命令必须使用实际运行环境的 Python：

```bash
/home/a/miniconda3/envs/aiagent/bin/python main.py --install-automation
```

安装程序读取当前 `sys.executable` 和应用目录，写入两条带固定标记的 cron：

- `@reboot` 启动一次自动检查。
- 每分钟运行一次 `--run-automation`。

因此把源码复制到新目录、切换 Python 环境或更新实际运行路径后，需要先卸载旧任务，再在新目录用目标解释器重新安装。部署代码时保留真实 `config.yaml`、`Records`、`AnalysisReports` 和 `Log`。

卸载使用同一实际环境：

```bash
/home/a/miniconda3/envs/aiagent/bin/python main.py --uninstall-automation
```

安装和卸载只管理 Linux cron 中带 AgentRecord 标记的行，不应改写用户其他 cron 任务。

## 12. 诊断与恢复

发生失败时可按以下顺序检查：

1. 在报告模式执行 `/status`，查看准确目标、当前任务、阻塞项和重试类别。
2. 查看 `Log/AgentRecord.log` 中对应时间的错误分类，不用 SQLite 的 `running` 单独推断任务仍活着。
3. 检查目标日记总结或 `_auto.md` 报告文件是否实际存在；真实文件是自动完成判断依据。
4. 检查 cron 是否指向实际目录和 `aiagent` 解释器，避免系统 Python 缺少依赖。
5. 配置或输入已经修正后使用 `/retry`；等价失败运行可复用已完成阶段。
6. 只有确认没有报告进程时，才删除可丢弃的 SQLite 主文件、`-wal` 和 `-shm` 重建缓存。

代码变更后的最低验证为：

```bash
/home/a/miniconda3/envs/aiagent/bin/python -m compileall -q AgentRecord tests
/home/a/miniconda3/envs/aiagent/bin/python -m unittest discover -s tests -v
```

文档、配置注释、命令帮助和实现应同时核对。尤其要确认周报与月报边界、自动任务顺序、JSON 契约、实际模型显示和 Token 统计没有发生描述漂移。
