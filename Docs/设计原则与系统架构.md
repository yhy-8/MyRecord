# AgentRecord 设计原则与系统架构

本文说明 AgentRecord 为什么这样设计、系统边界是什么，以及各代码模块如何协作。需要继续追踪模型调用和报告生成过程时，阅读[Agent 与报告流程](./Agent与报告流程.md)；需要查看 SQLite、自动任务、文件交付和故障恢复时，阅读[运行机制与数据](./运行机制与数据.md)。

## 1. 产品目标与边界

AgentRecord 是本地优先的个人记录和周期回顾工具。用户只需持续写日记，程序从原始记录生成昨日总结、自然周报和自然月报，不要求用户先分类，也不把记录过程变成与 AI 的对话。

```text
原始 Markdown 日记
  └─ 昨日简短总结（写回日记）
          ↓
自然周报
  ├─ 整理与回顾
  └─ 记录驱动的领域研究
          ↓
自然月报
  └─ 整理与回顾
```

三个派生产物的职责不同：

| 产物 | 输入范围 | 任务 | 是否联网 |
|---|---|---|---|
| 日记总结 | 单日日记 | 为以后浏览提供简短概括 | 否 |
| 周报 | 一个完整自然周 | 回顾本周，并从本周记录引出最多五个公开研究问题 | 是 |
| 月报 | 一个完整自然月 | 综合当月记录、近期总结和当月内完整周报 | 否 |

系统不再生成分析日报、每日信息简报或人物画像。月报也不重复周报的选题、搜索和研究。它们的删除不是功能缺失，而是为了让每种产物都有不重叠的阅读价值。

系统还明确不承担以下职责：

- 不把零散记录推导为人格定性、心理诊断或永久画像。
- 不代替用户作价值判断、现实决定或行为监督。
- 不把 SQLite 变成用户内容的唯一存储。
- 不让模型直接决定文件路径、来源归属、任务顺序和持久化方式。

## 2. 核心设计原则

### 2.1 原始日记是唯一事实源

`Records/YYYY-MM-DD.md` 保存用户实际写下的内容。日记总结、周报、月报、SQLite 状态和自动任务状态都是派生数据，可以重新生成。

这一原则带来三个结果：

1. 普通记录写入不依赖模型、网络、SQLite 或后台任务。
2. 报告读取失败不会妨碍继续记录，也不会损坏原始内容。
3. 数据库结构改变时无需迁移旧报告状态；确认没有任务运行后删除缓存数据库即可重建。

### 2.2 模型处理语义，中控处理确定性细节

模型适合总结、关联、研究和审查，不适合稳定维护编号、数组、来源映射、文件格式和执行状态。因此系统把职责分成两层：

- Agent 只完成一次明确的语义任务，返回一个字段很少的 JSON 对象。
- 中控拆分多项任务，分配编号，调用搜索，绑定来源，安排审查，渲染 Markdown，统计用量并写入文件和数据库。

例如，需要研究多个主题时，中控对每个记录组分别调用 Planner，再对每个主题分别调用 Researcher。模型从不一次返回一组嵌套小节，因此也不会把后一小节误塞进前一小节的 `paragraphs`。

### 2.3 JSON 用于协议，不用于排版

正式报告的四个 Agent 使用 JSON Output，因为 JSON 能可靠区分动作、正文、审核结果和失败原因。但 JSON 只承载最小标量字段，不让模型构造复杂文档树。

Markdown 标题、列表、记录依据、链接和报告元数据全部由程序生成。这样既利用模型接口的结构化输出能力，又把强细节留给确定性代码。

日记总结只有一段最终文本，没有多路分发或来源装配需求，因此直接使用文本响应，不额外包一层 JSON。

### 2.4 完整优先，在提示词中要求简洁

语义正文没有生成后的字符数上限。程序不会先让模型生成内容，再因为“太长”而截断或判废，也不会用一个抽象篇幅限制替代内容判断。

提示词要求模型在完整覆盖任务的前提下保持简洁、避免重复。配置中的 `max_tokens=100000` 只是在请求发出前设置的接口异常输出和成本安全预算；接口如果真的以 `length` 结束，程序把响应视为未完整交付，而不是正常报告。

输入上下文仍有边界。引用文件、历史总结、搜索摘要和单次 Agent 输入需要限制，以避免外部内容无界增长并保护接口上下文。输入安全边界与输出篇幅政策是两件不同的事。

### 2.5 派生状态必须可验证、可恢复

报告不是“模型返回成功”就算完成。系统只有在正文通过协议和审查、临时文件原子替换成功、SQLite 运行状态落为完成后，才把本次任务视为交付。

自动任务以实际日记总结和报告文件判断产物是否存在。SQLite 用于审计运行和复用安全阶段，但不单独证明某份报告已经交付。

### 2.6 来源必须由程序绑定

中控把周期内记录转换成稳定的 `R-*` 来源标识，把搜索结果转换成 `W-*` 标识。Agent 只写正文，不自行编造来源 ID 或 URL；最终报告由程序生成日期级来源标识（如 `R-20260727`），完整的指纹标识只保留在 Reviewer 输入和运行审计材料中。

搜索标题和摘要属于不可信外部输入，只是研究材料，不能改变系统指令。显式日记引用也只能落在 `Records` 目录内，不能借引用读取任意本地文件。

## 3. 总体架构

系统由记录链路、报告链路和调度链路组成：

```text
命令行 / 自动调度
        │
        ├─────────────── 记录链路 ───────────────┐
        │                                         ▼
        │                              journal.py → Records/
        │                                         │
        └─────────────── 报告链路 ───────────────┤
                                                  ▼
context.py → orchestrator.py → Agents → ai_client.py
                    │               │           │
                    │               └──── JSON / 搜索
                    ▼
             store.py + 报告临时文件
                    │
                    ▼
          AnalysisReports/Weekly 或 Monthly

automation.py → 持久队列、依赖顺序、重试和状态展示
```

记录链路短且独立：终端收到普通文本后，`journal.py` 立即追加 Markdown。报告链路较长，因为它需要构造上下文、分派多个 Agent、搜索、审查、缓存和原子交付。调度链路只决定何时运行这些既有能力，不复制报告逻辑。

## 4. 模块职责

| 模块 | 主要职责 | 明确不负责 |
|---|---|---|
| `settings.py` | 读取 `config.yaml`，解析模型、目录和自动任务配置 | 生成内容或维护报告状态 |
| `journal.py` | 追加记录、替换 `<summary>`、删除最后一条记录、读取日记 | 周报/月报和 SQLite |
| `cli/` | 命令解析、模式切换、交互输出和后台报告作业 | Agent 语义与数据结构 |
| `ai_client.py` | OpenAI 兼容模型请求、JSON Output、Token 遥测、第三方搜索、网络错误分类 | 决定报告流程和来源归属 |
| `agents/base.py` | 构造共同提示词、调用单个 Agent、解析单个 JSON 对象 | 文件、数据库、搜索和多任务编排 |
| `agents/*.py` | Retrospective、Planner、Researcher、Reviewer 的语义契约与字段校验 | Markdown 渲染和持久化 |
| `analysis/context.py` | 读取周期记录、解析引用、构造来源、计算报告路径和输入快照 | 调用模型 |
| `analysis/orchestrator.py` | 报告中控：顺序、拆组、Agent 调度、搜索、审查、来源绑定和交付 | 终端交互和定时安装 |
| `analysis/store.py` | SQLite 运行与阶段缓存、短事务、Token 汇总 | 保存权威日记或报告正文 |
| `analysis/automation.py` | 检测缺失产物、持久队列、前置屏障、重试、状态和系统任务安装 | 重新实现总结和报告算法 |
| `file_lock.py`、`logging_config.py` | 跨进程互斥和诊断日志 | 产品流程决策 |

模块边界遵循一个简单判断：能够被规则准确完成的事情留在程序内；必须理解自然语言含义的事情才交给模型。

## 5. 数据分层

```text
Records/                              权威原始记录
AnalysisReports/Weekly/               可阅读的周报
AnalysisReports/Monthly/              可阅读的月报
AnalysisReports/.analysis.sqlite3     可删除的运行与阶段缓存
AnalysisReports/.automation-state.json 可恢复的自动任务队列与错误状态
Log/AgentRecord.log                   诊断日志
```

这些文件的可靠性等级不同：

- `Records` 需要最高保护，所有写入集中在 `journal.py` 并使用 `.journal.lock`。
- 周报和月报是正式交付物，采用唯一临时文件和原子替换，手动版与自动版分别保存。
- SQLite 与自动任务状态用于恢复工作，不应被当作阅读报告的必要条件。
- 日志只用于诊断，不参与任务是否完成的判断。

## 6. 权限与信任边界

AI 不能直接读写文件、数据库或调用工具。它能看到的内容由中控显式组装：

- Retrospective 可看到本周期记录、允许的引用记录、近期总结，以及月报可用的周报材料。
- Planner 每次只看到一个由中控划定的本周记录组。
- Researcher 每次只看到一个查询和该查询的搜索摘要，看不到真实 URL 和来源编号。
- Reviewer 只看到待审正文及中控提供的核验材料。

用户日记中引用的 AI 文本仍标记为引用内容，不会被当成用户本人陈述。搜索结果、引用内容和历史报告都属于资料层，优先级低于系统和 Agent 契约。

## 7. 报告与自动任务的不变量

实现和文档都应保持以下规则：

- 周报始终先完成回顾与审查，再进行选题、固定搜索、研究和逐主题审查。
- 周报研究主题只从本周全部记录划分出的记录组产生；任何一天都不能被静默遗漏。
- 月报只做回顾，不调用 Planner、搜索或 Researcher。
- 自动任务严格按“昨日日记总结 → 上周报告 → 上月报告”处理队列；前项失败时后项等待。
- 手动报告和自动报告互不覆盖，均直接显示实际模型、耗时和 Token 用量。
- 模型不决定数组、编号、URL、Markdown、文件路径和任务完成状态。
- 语义输出不会只因为篇幅长而失败，但协议错误、不完整响应、错误来源和未通过审查仍会失败。
- 原始记录永远不依赖 SQLite；派生数据库不提供旧结构迁移和兼容层。

## 8. 阅读和修改代码时的判断顺序

修改系统前，可依次确认：

1. 需求改变的是产品边界、模型语义，还是确定性程序细节。
2. 该逻辑是否会影响原始日记这一事实源。
3. 多项输出能否由中控拆成单项调用，而不是增加复杂 JSON。
4. 新状态是否真的需要持久化；如果可以从文件重建，就不应进入权威数据层。
5. 失败后是否能从实际文件、SQLite 阶段或自动任务状态安全恢复。
6. README、三份设计文档、配置注释和测试是否仍描述同一行为。

这个顺序用于控制架构规模：新增代码只有在现有边界无法清楚承担实际需求时才有意义。
