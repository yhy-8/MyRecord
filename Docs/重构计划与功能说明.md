# AgentRecord 重构计划与功能说明（终版：服务端中枢实时同步，无 git）

> 本文是**重构计划与功能说明**，不包含代码实现。目标：把单机本地优先的
> AgentRecord 重构为「**服务端中枢实时同步 + 客户端薄记录**」两端架构，实现
> 多设备记录互通、云端 AI 生成报告并同步回各端。**已放弃 git**：需求是设备间
> 互通与实时，并不需要 git 的版本历史/审计，因此采用更直接的中枢同步模型。

---

## 0. 已确认决策（汇总）

| 决策点 | 结论 |
|---|---|
| 同步模型 | **服务端中枢实时同步**（无 git）；只要求设备间互通 |
| 数据空间 | 单一数据空间（服务端为中枢，非 git 仓库） |
| AI 归属 | **全部云端**：总结、周报、月报由服务端生成并扇出到各端 |
| 客户端职责 | 只记录原始日记 + 实时同步 + 查看；无 AI、无模型密钥、无本地自动化 |
| 记录时间精度 | **秒级即可**（条目以 entry_id 区分，不需毫秒） |
| `/d` 语义 | **仅在线可用**，先交互服务端确认，删除当天最新一条，写删除标记/垃圾桶 |
| 实时机制 | 客户端各端直连中枢，push 记录 → 中枢扇出到其他在线端；断网排队补齐 |
| 鉴权/传输 | HTTPS + 长令牌（服务端只存哈希、可撤销轮换）；身份标识用普通 `device_id`，不做设备签名 |
| 命令行 | **统一单模式，共 7 个命令**：`/v /c /h /d /status /retry /model`，去除 `/mode` |
| 客户端本地存储 | **只存服务器 IP + 令牌**；同步所有 `Records/` 与报告 |
| 部署 | 裸机 systemd，服务端明文存储、root 运行，不做加密/权限加固 |
| 不入中枢的数据 | 客户端本地 `Log/`、本地令牌文件；模型密钥只在服务端且不入数据空间 |

## 0.1 已确认微调（2024-08-25 定稿，作为两端实现契约）

实现前由用户确认的细化结论，已固化到本文档：

1. **报告与 Records 实时同步到本地**：云端（服务端中枢）所有报告和 `Records/` 在客户端本地都有完整副本。云端只负责「AI 生成报告并扇出到各端」与「整合 Records 保证各端统一」，不承载本地阅读。
2. **同步触发**：客户端每记录一条**立即 push** 到云端；云端扇出后，客户端**每 1 分钟向云端询问拉取**并对账；收到扇出即拉取。push 即时，轮询间隔固定为 1 分钟。
3. **Records 渲染**：客户端**本地渲染** `Records/YYYY-MM-DD.md`（沿用现有渲染方案）；服务端同样渲染服务端数据空间内的 Records，用于聚合与扇出。
4. **不做 `/v` 查看报告**：报告效果建议用专用 Markdown 阅读软件打开阅读；客户端不实现报告 `/v` 查看。命令不再包含报告查看。
5. **目录结构**：删除现有 `AgentRecord/` 包，分别建立两个英文目录：`server/`（服务端中枢：hub + AI 工作 + 鉴权 + 存储 + 部署）与 `client/`（薄客户端：日记写入 + 同步 + 交互命令）。
6. **运行环境**：统一使用 conda 的 `aiagent` 环境验证（`conda activate aiagent`）。

## 1. 总体架构

```
┌────────────┐     ┌────────────┐     ┌────────────┐
│ 客户端 A      │     │ 服务端中枢     │     │ 客户端 B      │
│ (手机/桌面)  │◄───►│ 数据合并 + AI  │◄───►│ (桌面/手机)  │
│  记录 + 同步  │     │ 扇出 + 鉴权/安全│     │  记录 + 同步  │
└────────────┘     └────────────┘     └────────────┘
```

- 各设备直连中枢；中枢保证顺序合并、扇出、云端 AI、鉴权与数据安全。
- 设备离线时本地照常记录（离线优先），上线后按时间戳/条目 ID 对账补齐。
- 客户端不落 AI；`config.yaml` 的模型密钥只在服务端。

---

## 2. 时间与条目模型（合并的基础）

- 每条记录 = { **entry_id**, ts(秒), tag, text, device_id }。
- **entry_id = device_id + 本设备单调递增序号**（不依赖墙钟），保证跨设备唯一并按序。
- `ts` **秒级**时间戳用于**展示与排序**；设备时钟偏差不影响合并正确性（排序仅展示用）。
- 每天仍是 `Records/YYYY-MM-DD.md` 容器，记录行按 `ts` 写入；服务端渲染同一容器结构。

### 2.1 为什么用 entry_id 而不是纯时间戳
纯时间戳（即便秒级）跨设备不唯一、受时钟偏斜影响（撞秒、序乱、删错）。entry_id 天然唯一且
单调，是合并、对账、删除标记的稳定引用；时间戳只负责"人看得懂的排序"。这是对
"按时间标记删除"方案的必要加固。时间戳不需要毫秒级，因为每一条由 entry_id 区分。

---

## 3. 同步与合并语义

- **追加合并（append）**：各设备离线各自追加本日条目；上线后向中枢推送新条目，
  中枢按 entry_id 去重合并，并把别的设备的新条目扇出/供拉取。无并发覆盖。
- **对账（reconcile）**：设备上线时以中枢为准补齐缺失条目、并按 tombstone 移除已删条目
 （见 §4），不会把已删条目推回（防复活）。
- **离线队列**：未推送的新条目本地缓存，断网照常写；恢复后依次补齐。
  本地写入永不因同步失败回滚。

---

## 4. `/d` 删除（垃圾桶语义，与回收站类似）

- `/d` **仅在线可用**，请求中枢确认；且**只能删除当天最新一条，不能跨天删除**。
- 删除采用**垃圾桶（回收站）语义**，不污染原始记录：
  - **原始记录只标记**：`Records/YYYY-MM-DD.md` 在被删位置写入一个**删除标记占位**
    （注明这里删过一条，含其 entry_id），**不含被删正文**，原始流保持干净。
  - **被删正文移到独立垃圾桶文件**（在 Records **之外**，如 `Trash/`，独立存放区），
    完整保留原内容，供查看与恢复。
- **防复活规则**：删除标记按 entry_id 引用；离线设备 B 上线时，若本地存有被标记的
  entry_id → 本地同样移除该条，且**不推回**。从而 A 在线删除后，B 上线不会把已删内容
  重新同步上云。
- 垃圾桶内容同样随中枢同步到各端（可查看/恢复），但其不参与"原始记录合并"。
- 删除标记按 entry_id（而非纯时间戳）引用，避免时钟偏斜删错。
- **不做硬删除**：删除 = 原始记录占位标记 + 垃圾桶保留原正文；均可审计与找回。

## 5. 传输与数据安全（已定：明文 root，去签名）

传输安全：
- 仅 HTTPS(TLS 1.2+)；不接受明文。
- 设备鉴权用**长令牌**：`Authorization` 携带；服务端**只存令牌哈希**（argon2id），
  支持单独撤销与轮换；比对为常量时间；限速 + 失败锁定防爆破。

数据本身：
- **设备标识 = 普通 `device_id` 字段（纯标签）**，用于"知道是谁写的 / 发现非本设备"。
  **不做设备数字签名（ed25519）**：用户只关心"哪台设备写的"，不要求密码学可证实出处，
  故移除签名。代价：`device_id` 可被伪造，但对"设备标签"目的无影响。
- **服务端明文存储、直接以 root 运行**；不做加密备份，不做目录/权限加固。
- **防删除（垃圾桶语义，非加密）**：删除 = 原始记录占位标记 + 正文入垃圾桶；
  中枢 append-only，无硬删除；简单定期备份供恢复。
- 窄协议面、无 shell、无任意文件/路径接口；模型密钥与数据空间隔离，不进日志。

### 6.1 统一命令行（单模式，共 7 个命令）

去掉 `/mode`，不再区分记录/报告模式，统一为一个交互入口：

| 命令 | 作用 |
|---|---|
| `/v` | 查看日记（可传日期）；查看同步到的报告 |
| `/c` | 清屏 |
| `/h` | 帮助 |
| `/d` | 在线删除当天最新一条（服务端确认 → 垃圾桶） |
| `/status` | 查看服务端当前 AI 自动任务状态 |
| `/retry` | 按队列重试服务端 AI 自动任务 |
| `/model` | 永久切换所有 AI 任务的模型 |

普通输入即写当天记录；同步自动进行（写后即时 push，收到扇出即拉取）。

Windows：沿用 PyInstaller 出 `AgentRecord.exe`（交互）+ `AgentRecordBackground.exe`
（后台实时同步循环）；客户端同步逻辑用纯 Python（http），不依赖 git 二进制。

## 9. 不变量

**保留**：原始日记是唯一事实源；普通记录写入不依赖模型/网络/报告生成；
手动与自动报告互不覆盖；模型拿不到真实路径/密钥；URL/来源由程序渲染。

**新增**：本地写入永不因同步失败回滚；跨设备合并按 entry_id 去重、不并发覆盖；
删除只做 tombstone 不做硬删除（防复活、防删除攻击）；模型密钥只在服务端且不入数据空间/日志。

## 10. 已确认的细化决策

1. **条目唯一引用 = entry_id（device_id+单调序号）**；时间戳**秒级**、只用于展示排序，不需毫秒。
2. **删除 = 垃圾桶语义**：被删正文移到 Records **之外**的独立垃圾桶文件（回收站），
   原始记录只留**删除标记占位**；tombstone 不污染原始流。
3. 每日文件仍是 `Records/YYYY-MM-DD.md`，客户端与服务端按同一格式渲染。
4. `/d` **只删当天最新一条，不能跨天删除**。
5. 报告仍为 `AnalysisReports/` 的 Markdown，服务端渲染并同步到各端。

以上是**已冻结的产品决策**；本文档到此为止，是给新窗口实现 agent 的移交契约。

## 11. 移交说明：P0 设计点（已确认，见 §0.1）

原计划把以下设计点交给实现方先行确认；现已在 §0.1 定稿，本节保留记录。

以下内容本计划**有意未定死**，交给实现 agent 在 P0 设计、并在动码前与用户确认。
这会避免“文档假装已定、实现时才发现歧义”。

1. **同步协议报文**：push / 拉取 / 对账的接口路径与消息结构；tombstone、离线队列的
   持久化格式。需要与用户确认协议草案。
2. **实时扇出机制**：WebSocket / SSE / 长轮询三选一（考虑 Windows 打包与简单性）。
3. **设备注册与首登流程**：第一台设备如何绑定、令牌如何签发与轮换、如何发现非本设备。
4. **Records 文件 ↔ 条目存储的关系**：客户端是直接写当天 `Records/YYYY-MM-DD.md`，
   中枢按条目存储再去重/对账/渲染回文件；这个双向映射必须先在 P0 讲清，避免两端实现打架。
5. **日总结 `<summary>` 归属**：云端写回当天文件，说明它如何在同步中与记录流共存
   （与垃圾桶占位一样，属“服务端独占写”的区域）。
6. **旧数据迁移**：现有单机 `Records/` 如何作为首推种子建立新服务器；首次 setup 步骤。
7. **命令 `/v` 如何查看报告**、`/status` 的服务端状态接口返回结构。

实现顺序仍按 §8：P0（上述 1–7 决策并确认）→ P1（服务端 hub）→ P2（客户端薄化）→ …
