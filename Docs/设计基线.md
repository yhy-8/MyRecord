# MyRecord 设计基线（单一权威说明）

本文是 MyRecord 的**唯一权威设计基线文档**，整合此前分散在各处的设计说明（根
`README.md`、`server/README.md`、`client/README.md`、`Docs/代码结构.md`、
`Docs/部署指南.md`，以及已并入本文的 `Docs/安全、通信与日志.md`）为一份完整、自洽、
相互不矛盾的设计依据。
代码与测试以本文为准；本文与上述旧文档冲突时，以本文为准（旧文档随后会收敛指向本文）。

> 代码依据：`server/hub/`、`server/ai/`、`client/`、`server/main.py`、`server/config.example.yaml`（提交的配置模板）。

---

## 1. 项目定位与总体架构

MyRecord 是一个**本地优先、多设备云端同步**的个人记录与周期回顾工具。你像写日记一样自由记录，
不预先分类，也不把记录过程变成与 AI 的对话。

架构为**服务端中枢 + 客户端薄端**两段：

- **服务端（`server/`）**：数据中枢 —— 设备鉴权、条目合并/对账/扇出、垃圾桶、TLS、日志，
  以及全部云端 AI（每日总结、自然周报、自然月报）。模型密钥只存服务端。
- **客户端（`client/`）**：薄记录端 —— 只负责写当天日记、实时同步、查看与常用命令；
  不保存模型密钥、不做本地 AI。

两个目录**严格分离、各自独立部署**：二者只有极少代码重合（原子写入 `atomic_write`、日记文件格式
`render`），直接各自内置一份本地小工具，不做跨模块导入、不共用 `common/`。以启动命令决定它作为
客户端还是服务端运行（`python -m server.main run` / `python -m client`）。仓库根还保留联合开发/测试/文档脚手架。

**最终原则（全项目最重要的一条）**：

> **原始日记是唯一事实源。** 总结、报告、自动任务状态、来源表都是可重建的**派生**数据，
> 任何派生数据都不再反过来作为其他派生数据的输入（不允许摘要层层传递造成信息损失）。

## 2. 端职责划分

> **两端严格分离**：客户端与服务端各自内置一份 `atomic_write.py`（原子文件写入）与 `render.py`
> （日记文件格式），互不导入、不共用 `common/`，可各自独立部署；以启动命令决定角色
> （`python -m server.main run` / `python -m client`）。

### 服务端（中枢 + 云端 AI）

| 模块 | 职责 |
|---|---|
| `main.py` | CLI：`run`（起 hub + AI 自动任务线程，强制 TLS）、`token`（单一连接凭证管理）、`cert`（自签 TLS 证书）、`deploy`（一键 systemd）、`import`（旧数据导入）、`render`（重渲染 Records） |
| `config.py` / `config.example.yaml` | 读取服务端配置（监听、数据目录、模型、重试、自动任务、TLS 默认路径）。`config.example.yaml` 是提交的**空白模板**；运行时读取 `config.yaml`（含 api_key，已 gitignore），由用户复制模板并填入密钥 |
| `hub/server.py` | HTTP 同步服务（stdlib ThreadingHTTPServer + ssl）：`/api/sync/push\|pull\|longpoll`、`/api/entries/delete`、`/api/status`、`/api/reports`、`/api/admin/*`；Bearer + device_id 鉴权 |
| `hub/store.py` | 权威条目存储（`state.json`）：append-only 合并（按 entry_id 去重）、tombstone、垃圾桶、设备令牌、全局 `version` 同步游标、长轮询等待、增量拉取 |
| `hub/auth.py` | 连接凭证令牌哈希（scrypt，加盐、常量时间），只存哈希不落明文 |
| `hub/render.py` | 日记文件格式（服务端渲染/解析；客户端本地 `client/render.py` 为同款镜像，互不引用）：渲染 entry 标记 / tombstone 占位 / `<summary>` 区域，并反向解析文件为条目列表（兼容新旧标记） |
| `ai/settings.py` | 运行配置、目录与模型选择 |
| `ai/ai_client.py` | OpenAI 兼容模型请求、HTTP/thinking/JSON 输出、Token 遥测、错误分类 |
| `ai/journal.py` | 原始日记读写与 `<summary>` 区域更新（AI 只能通过这里写日记） |
| `ai/agents/` | 单模块：AgentSpec、提示词构造（含 JSON 结构与示例）、调用与确定性校验 |
| `ai/analysis/context.py` | 周期范围、按天分块并标注行号的记录流、报告路径 |
| `ai/analysis/orchestrator.py` | 单次 Report Agent 调用、纯 JSON（summary+references）解析与引用校验、Token 累计、头部审计元数据、文末来源表、原子交付报告 |
| `ai/analysis/automation.py` | 简调度器：每 15 分钟缺失检测、失败后 30 分钟重试、按失败次数上限停止、每任务状态持久化 |
| `ai/file_lock.py`、`ai/logging_config.py` | 跨进程互斥、有界诊断日志 |

### 客户端（薄端）

| 模块 | 职责 |
|---|---|
| `__main__.py` | 入口：`python -m client` → `cli.run_interactive()` |
| `cli.py` | 交互主循环：7 个命令路由；普通输入 → 写本地 + push；启动 full_sync；后台**持续同步**线程（连接即完整对账，断线自动重连补齐） |
| `terminal.py` | 跨平台终端输入：逐字符、Unicode 感知整字符退格（Windows 控制台事件 / POSIX raw），并处理后台线程通知展示 |
| `identity.py` | 连接凭证与设备身份：读写 `credentials.json`（单一共享 token）；`device_name()` 自报本机名；`make_entry_id(date,ts,text)` 生成设备无关确定性 id |
| `atomic_write.py` | 原子文件写入（客户端自带小工具，与服务端各自独立） |
| `render.py` | 日记文件格式本地渲染（标记常量/entry/tombstone/day_header；客户端自带，与服务端 hub/render.py 同款互不引用） |
| `journal.py` | 本地日记写入与对账：按天 `Records/YYYY-MM-DD.md` 原子追加、对账补齐、tombstone 移除（渲染格式用客户端本地 `render.py`） |
| `file_lock.py` | 跨进程互斥（原子写） |
| `sync.py` | 与中枢同步：`push_new` / `send_pending` / `pull` / `longpoll` / `full_sync` / `sync_reports` / `delete_latest` / `status` / `admin_retry` / `admin_set_model`（断线重连后用 `full_sync` 做完整对账） |
| `config.py` / `config.example.yaml` | 本地配置（服务器地址、数据目录、长轮询秒数）。`config.example.yaml` 是提交的模板；运行时读取 `config.yaml`（已 gitignore），由用户复制并填服务器地址 |

客户端**不密集轮询云端**，且**同步是全自动、无感知的**：

1. 启动时自动一次完整同步（拉取对账 + 冲刷离线队列 + 同步报告）。
2. 运行期间后台线程保持一条**长连接（长轮询）**，服务端有更新即扇出返回并立即应用，超时立即重挂。
3. **服务端离线再上线后，后台线程会自动重新连接并完整对账**，无需手动同步。

断网时本地照常记录并进 `outbox.json` 离线队列，恢复后自动冲刷补齐。

## 3. 数据模型与记录格式

### 3.1 每条记录（entry）

日记文件中每条记录是一块：

```text
<!-- myrecord-id:<entry_id> -->
<!-- myrecord-device:<设备名> -->        （可选，便于区分哪台设备写的）
**HH:MM [设备名]:** 正文                （记录的可视头部行）
```

- **entry_id**：内容派生、设备无关 —— `sha256(date + ts + tag + text)` 取前 16 位。同一记录在
  任何端算出同一 id，离线多端上线后按 id 去重合并；ts 参与哈希，避免同一天重复写相同句子被误合并。
- **tag**：普通记录无标签；仅“引用”等特殊记录带标签（如 `[引用]`）。
- **删除**：写 tombstone 占位（**只有一行，不含正文**），正文入垃圾桶，不做硬删除，防“已删条目复活”。

```text
<!-- myrecord-tombstone-id:<entry_id> -->
```

### 3.2 每日日记文件

每天一个 `Records/YYYY-MM-DD.md`：

```text
# YYYY-MM-DD

<summary>
...每日总结正文...
</summary>

---
## 原始记录流

<!-- myrecord-id:... -->
**HH:MM:** 正文
...
```

`<summary>` 区域由服务端 AI 独占写（见 §8.8），原始记录流部分由两端同步写入。

### 3.3 向后兼容

旧数据（`agentrecord-*` 标记、远古无标记的裸 `**HH:MM:** 正文`）无需迁移：解析器原生向后兼容；
无 entry_id 的记录自动生成 legacy id；任何旧标记注释都不会混入正文，AI 只读正文文本。

## 4. 同步与对账协议

| 端点 | 用途 |
|---|---|
| `POST /api/sync/push` | 推送新条目（`{entries, version}`） |
| `GET /api/sync/pull?version=N` | 拉取增量 |
| `GET /api/sync/longpoll?version=N` | 长轮询扇出 |
| `POST /api/entries/delete` | 在线删除当天最新一条 |
| `GET /api/status` | 服务端状态 |
| `GET /api/reports` + `/api/reports/<kind>/<name>` | 报告列表 / 内容 |
| `GET /api/health` | 存活探针（无需鉴权） |
| `POST /api/admin/retry`、`/api/admin/model` | AI 任务重试 / 切换模型 |

鉴权：全部接口需 `Authorization: Bearer <token>` + `X-Device-Id`（客户端自报本机名）。
`store.append_entries` 按 `entry_id` 去重合并，维护全局 `version` 游标作为增量边界。

## 5. 连接凭证与传输加密（强制）

### 5.1 连接凭证（单一共享 token）

- 签发：`python -m server.main token create` 用 `secrets.token_urlsafe(32)`
  生成约 43 个 URL 安全字符的超长随机 token，打印一次后不再可见。重签（覆盖旧 token）会提示二次确认。
- **服务端只存哈希**：`hub/auth.py` 用 `hashlib.scrypt`（加盐、`N=2^14`、常量时间比较）存为
  `scrypt$N$r$p$salt$hash`。数据空间泄露也无法反推明文。
- **单一共享凭证**：不绑定设备；设备由各端自报 `X-Device-Id` 区分。`create` 覆盖旧 token（无多凭证/多设备）。
- **无凭证/凭证错误**：客户端只能本地记录，无法把修改传上服务端或拉取/删除云端数据。
- **爆破防护**：连续鉴权失败 5 次按设备锁定 60 秒，并记日志。

### 5.2 传输加密（强制 TLS，自签直连）

- `python -m server.main run` 未配置 TLS 会**拒绝启动**（禁止明文，返回码 2）。
- `python -m server.main cert` 生成**自签证书（同时具备 CA 能力，有效期 10 年）**及私钥，写入
  `data/tls/server.crt` 与 `server.key`；`--ip`/`--dns`/`--cn` 指定 SAN 覆盖客户端连接地址。
- 客户端 `config.yaml`：`server_url` 为 `https://…`，`verify` 指向复制过来的 `server.crt` 校验收信。
- `ThreadingHTTPServer` 直接把监听 socket 用 `SSLContext` 包裹成直连 HTTPS，无需反向代理。
- 信任锚是**首次分发（TOFU）**：首次可靠地把 `server.crt` 送到客户端并手动指向它，此后每次严格验真。

## 7. 日志与审计

服务端日志统一写 `data/Log/MyRecord.log`（RotatingFileHandler，单文件 5MB、保留 2 份备份）。

记录的事件：客户端连接/鉴权（`auth_failed` / `auth_locked_out` / `auth_missing_device` /
`status_request`）、对日志的修改（`sync_push` / `sync_delete` / `sync_pull` / `sync_longpoll` /
`report_read` / `reports_list`）、AI 报告生成状况（`analysis_started/completed/failed`、
`agent_start` / `agent_completed` / `agent_failed`、`daily_summary_validation_failed`）、自动任务调度
（初始化失败、配置无效、scheduler 异常、`automation_retry_*`）。

**隐私原则（不记录）**：日记正文、模型密钥与 token 明文（模型密钥只在服务端 `config.yaml`，
明文保存于服务端本地配置，绝不写入数据空间或日志）。

## 8. 云端 AI 分析设计

### 8.1 总原则：原始记录是唯一事实源

周报 / 月报**只读取各自时间范围内的完整原始记录流**（按日期分隔的 `Records/YYYY-MM-DD.md`），
作为**唯一事实来源**。报告**不读取**每日总结、旧周报、旧月报、引用历史记录或其他任何历史报告，
避免“摘要层层传递”造成信息损失。原始记录流是原始事实，派生的总结/报告不得再作为事实输入。

### 8.2 报告生成流程：单次 Report Agent

每周 / 每月报告由**单次 Report Agent 一次性直接生成完整报告**。其分工为：

- **Agent**：一次性阅读中控提供的按天分块记录流，整理内容，并返回**纯 JSON 对象**：`summary`
  （含 `[n]` 引用编号的报告正文）+ `references`（每个引用编号对应的来源）。
- **中控（程序）**：构造提示词（含任务、引用规则、JSON 输出结构与示例）、拼接记录流（按天分块 +
  行号）、解析返回的 JSON、校验引用合法性、写入头部审计元数据与文末来源表、原子交付报告。
  中控不做 AI 审核。

### 8.3 中控输入：按天分块 + 行号

记录流**按天分组**，每天一个块。**块首行是 `[YYYYMMDD]`**（英文方括号），**块内每行格式为
`行号: 内容`**（英文冒号）。所有块按日期顺序拼接。

具体约定：

- **行号**：一条记录在**其所属日期文件**中的 1-based 行号，定位到该记录的可视头部行（`**HH:MM:**`
  开头的那一行）；引用来源 `R-YYYYMMDD-行号` 中的行号与之完全一致。

输入呈现形如：

```text
[20260816]
1: 今天去了公园，天气很好。
2: 下午和朋友聊天，讨论了项目计划。
[20260817]
1: 早上开会，确定了本周目标。
```

### 8.4 提示词与 Agent 交付：纯 JSON（summary + references）

提示词明确：

- **任务**：基于输入记录生成周报 / 月报的 `summary`，并对 `references` 中的每个编号给出来源。
- **引用规则**：总结正文引用具体信息时，在句子末尾标注引用编号，如 `[1]`、`[2]`（从 1 开始，
  连续编号）；在 `references` 数组中列出每个编号对应的来源。
- **来源格式**（全部英文半角标点）：
  - 单行：`R-YYYYMMDD-行号`，例如 `R-20260816-1`。
  - 多行连续：`R-YYYYMMDD-起始行-结束行`，例如 `R-20260816-2-3`。
- **只引用输入中实际出现的行号，不得编造**；若信息来自连续多行则合并为一个引用，单行只写一个行号。
- 提示词包含**至少一个完整示例**（输入片段 + 输出 JSON），展示单行与多行引用的写法。

Agent 必须返回**纯 JSON 对象**（不要任何额外文字或 Markdown 代码围栏），结构如下：

```json
{
  "summary": "包含引用编号的总结文本",
  "references": [
    {"id": 1, "source": "R-20260816-1"},
    {"id": 2, "source": "R-20260816-2-3"}
  ]
}
```

`summary` 是字符串（内文可用 Markdown 排版，可含 `[1]`、`[2]` 等标记）；`references` 数组按 `id`
升序排列。

### 8.5 输出解析与引用校验（确定性，无 AI 审核）

- 程序用 JSON 解析 `summary` 与 `references`；若模型返回被代码围栏包裹，先去除首尾 ``` 标记再解析。
- 解析后逐一校验每个 `reference`（中控确定性校验，不调模型）：
  1. **格式**：符合 `R-YYYYMMDD-行号` 或 `R-YYYYMMDD-起始行-结束行`。
  2. **日期**：该 `YYYYMMDD` 属于本周期范围。
  3. **行号范围**：`起始 ≤ 结束`，且不超过该日期块的最大行号。
- **无效引用直接丢弃**（记录日志），不重试。
- 若整个响应不是合法 JSON、`summary` 为空或不是文本，本次报告生成失败。

### 8.6 来源表（中控生成）

来源表由中控根据**校验后的 `references`** 生成（不额外调模型），例如：

```text
## 来源
[1] R-20260816-1
[2] R-20260816-2-3
```

- **Agent 不参与**来源表的排版与写入；它只交付 `references` 数据。
- 来源表只列出模型交付且通过 §8.5 校验的引用。

### 8.7 报告文件布局与统一生成

- 手动与自动共用**相同的生成流程**，调用同一个入口，报告文件走统一路径。
- 报告文件路径（无 `_manual` / `_auto` 后缀）：

```text
AnalysisReports/Weekly/YYYY-MM-DD_to_YYYY-MM-DD.md
AnalysisReports/Monthly/YYYY-MM.md
```

- **手动重新生成时直接覆盖**该时间范围对应的原有报告文件（同路径原子替换）。
- 自动任务检测“该周期报告是否已生成”时，同样检查**这个唯一路径**是否存在。

### 8.8 报告头部审计元数据

报告头部保留审计元数据：

```text
# <报告名>

> 生成时间：YYYY-MM-DD HH:MM
> 使用模型：<model>
> 生成耗时：…
> Token 用量：…（输入/输出/缓存命中/缓存未命中）
> 原始日记范围：YYYY-MM-DD 至 YYYY-MM-DD
> 分析运行：<run_id>
```

这些元数据来自中控的确定性统计（Timer、UsageAccumulator 累计的真实调用遥测），**不来自模型**。

### 8.9 每日总结（独立速览；报告不依赖它）

每日总结由服务端把一天内容的要点写入该日日记顶部 `<summary>` 区域，仅作当日速览。
它有**独立的确定性格式校验 + 有界格式重试**（非 AI 审核）：拒绝 JSON / 代码围栏 / 包装标签 /
正文内标题；不合格时附“中控格式修正”再试（`daily_summary_retry_limit`，默认 2）；
防陈旧写入（写入前比对日记内容哈希，生成期间被改则不写）。

报告不读取每日总结（见 §8.1）：每日总结不是周/月报的事实输入，二者相互解耦。

## 9. 自动化任务（简单重试机制）

服务端有一个后台调度线程，只做两件事：**每 15 分钟检测一次缺失**，并**执行所有到期任务**。三种任务
（昨日日记总结、上一完整自然周周报、上一完整自然月月报）**互相独立、互不依赖**——报告只读本周期原始
记录流（§8），不读总结或其它报告，因此**无顺序要求**，检测到即可各自独立生成。

### 9.1 缺失检测（每 15 分钟）

判定「任务是否存在」只依据两件事：

- **产物文件是否存在**：周/月报 = 该周期报告文件是否已生成；日总结 = 昨日日记的 `<summary>` 是否已写。
- **对比当前时间**：周期目标由当前时间推出（昨日、上一完整自然周 = 周一起 7 天、上一完整自然月）。

新发现缺失 → 该任务**立即到期**开始首次生成；周期内无任何记录的任务不视为缺失（无事可做）。

### 9.2 失败重试（不区分失败类型）

- **不区分任何失败类型**（网络 / 内容 / 配置一视同仁）：生成失败即记一次失败，**立刻开始计时**，
  **30 分钟后自动重试**。
- 每个任务有**各自的重试次数参数**（`daily_summary_retry_limit` / `weekly_report_retry_limit` /
  `monthly_report_retry_limit`，**默认 2**，即首次后再重试 2 次，共执行 3 次）。达上限后**停止自动重试**。
- 每次生成后保存该任务状态：`status`（`ok` 完成 / `failed` 失败待重试 / `blocked` 已达上限）、
  `error`（失败原因）、`attempts`（已执行次数）、`next_retry_at`（下次重试时间；达上限后为空）。

### 9.3 手动 /retry

`/retry` 命令**直接重试全部失败任务**（重置各自计数、立即再试一轮），不按顺序、不做依赖约束。

### 9.4 状态持久化

`.automation-state.json` 保存每次检测时间与每个任务的状态（上文 9.2 字段），供 `/status` 查看。
周期目标判定：周 = 周一起算的完整 7 天；月 = 自然月；报告只对该范围原始记录流生成（§8.7）。

## 10. 部署与备份

- 服务端：`pip install -r server/requirements.txt`，`python -m server.main run`（强制 TLS）。
- 客户端：`python -m client`（启动自动同步 + 长连接）。
- 服务端子命令详见 §2 模块表；`cert` 生成自签 TLS。
- `server/deploy/`：systemd 单元（`myrecord-server.service`）、备份（`backup.sh`，tar 保留 N 份）、
  恢复（`restore.sh`）。
