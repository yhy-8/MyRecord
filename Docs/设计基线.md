# MyRecord 设计基线（单一权威说明）

本文是 MyRecord 的**唯一权威设计基线文档**，定义项目的设计规则。架构、同步、鉴权/TLS、
存储、日志与云端 AI 的权威设计均以本文为准。

> 代码依据：`server/hub/`、`server/ai/`、`client/`、`server/main.py`、`server/config.example.yaml`（提交的配置模板）。

---

## 1. 项目定位与总体架构

MyRecord 是一个**本地优先、多设备云端同步**的个人记录与周期回顾工具。你像写日记一样自由记录，
不预先分类，也不把记录过程变成与 AI 的对话。

架构为**服务端中枢 + 客户端薄端**两段：

- **服务端（`server/`）**：数据中枢 —— 设备鉴权、条目合并/对账/扇出、垃圾桶、TLS、日志，
  以及全部云端 AI（每日总结、自然周报、自然月报）。模型密钥只存服务端。
- **客户端（`client/`）**：薄记录端 —— 只负责写当天日记、实时同步、查看与常用命令；
  不保存模型密钥、不做本地 AI。

两个目录**严格分离、各自独立部署**：二者只有极少代码重合（原子写入 `atomic_write`、日记文件格式
`render`），直接各自内置一份本地小工具，不做跨模块导入、不共用 `common/`。以启动命令决定它作为
客户端还是服务端运行（`python -m server.main run` / `python -m client`）。仓库根还保留联合开发/测试/文档脚手架。

**最终原则（全项目最重要的一条）**：

> **原始日记是唯一事实源。** 总结、报告、自动任务状态、来源表都是可重建的**派生**数据，
> 任何派生数据都不再反过来作为其他派生数据的输入（不允许摘要层层传递造成信息损失）。

**数据安全与唯一权威（全项目第二条生命线）**：

> **云端是唯一权威记录。** 所有客户端**只能更新“今天”（UTC+8 自然日）**的日记；昨天及以前为
> **只读**——客户端只能拉取、不能推送。客户端本地历史日记若与云端不一致，一律**以云端为准整文件覆盖**，
> 从而杜绝任何一台客户端改写或毁坏以往的日记。

> **“今天”是唯一可写窗口；过期未同步的部分直接作废。** 客户端把当天记录写入本地、并在当天推送到云端；
> 若某条记录未能在当天同步、拖到了第二天，该条**不再推送**（客户端主动丢弃 `outbox.json` 中 `date < 今天`
> 的条目），即使客户端强推，服务端也**拒绝**（条目的 `date` 早于今天即拒绝）。时间基准为 **UTC+8**，
> **固定写死在代码中**（非配置项），多端、跨时区因此一致。

## 2. 端职责划分

> **两端严格分离**：客户端与服务端各自内置一份 `atomic_write.py`（原子文件写入）与 `render.py`
> （日记文件格式），互不导入、不共用 `common/`，可各自独立部署；以启动命令决定角色
> （`python -m server.main run` / `python -m client`）。

### 服务端（中枢 + 云端 AI）

| 模块 | 职责 |
|---|---|
| `main.py` | CLI：`run`（起 hub + AI 自动任务线程，强制 TLS）、`token`（单一连接凭证管理）、`cert`（自签 TLS 证书）、`deploy`（一键 systemd）、`import`（导入既有 Records）、`render`（重渲染 Records）、`report`（手动生成周/月报，同流程直接覆盖） |
| `config.py` / `config.example.yaml` | 读取服务端配置（监听、数据目录、模型、重试、自动任务）。`config.example.yaml` 是提交的**空白模板**；运行时读取 `config.yaml`（含 api_key，已 gitignore），由用户复制模板并填入密钥。TLS 证书路径**不在** config 中配置：由 `cert` 统一定点生成到 `<data_dir>/tls/` |
| `hub/server.py` | HTTP 同步服务（stdlib ThreadingHTTPServer + ssl）：`/api/sync/push\|pull\|longpoll`、`/api/entries/delete`、`/api/records`、`/api/records/<date>`（历史日整文件拉取）、`/api/status`、`/api/reports`、`/api/admin/*`；Bearer + device_id 鉴权 |
| `hub/store.py` | 权威存储（`state.json`）**仅“今天”**的条目/tombstone/垃圾桶/设备令牌/全局 `version` 游标；append-only 合并（按 entry_id 去重，仅今天）、`wait_for_change`（长轮询）、`pull(version)`（仅今天增量）、历史日以 `Records/*.md` 整文件为权威 |
| `hub/auth.py` | 连接凭证令牌哈希（scrypt，加盐、常量时间），只存哈希不落明文 |
| `hub/render.py` | 日记文件格式（新格式；客户端本地 `client/render.py` 为同款镜像，互不引用）：渲染 entry 标记 / tombstone 占位 / `<summary>` 区域；**不再解析旧格式/裸记录**（历史日整文件为准，见 §4） |
| `hub/backup.py` | 内置数据备份调度（见 §10）：距上次成功备份满 7 天（或从未备份）即以**子进程**执行 `server/deploy/backup.sh`，把整个数据空间打成单个 gzip tar 快照并保留最近 N 份；状态持久化在 `data/.backup-state.json`，服务停止期间错过的备份在下次启动后补跑 |
| `ai/settings.py` | 运行配置、目录与模型选择 |
| `ai/ai_client.py` | OpenAI 兼容模型请求、HTTP/thinking/JSON 输出、Token 遥测、错误分类 |
| `ai/journal.py` | 原始日记读写与 `<summary>` 区域更新（AI 只能通过这里写日记） |
| `ai/agents/` | 单模块：AgentSpec、提示词构造（含 JSON 结构与示例）、调用与确定性校验 |
| `ai/analysis/context.py` | 周期范围、按天分块并标注行号的记录流、报告路径 |
| `ai/analysis/orchestrator.py` | 单次 Report Agent 调用、纯 JSON（summary+references）解析与引用校验、Token 累计、头部审计元数据、文末来源表、原子交付报告 |
| `ai/analysis/automation.py` | 简调度器：每 15 分钟缺失检测、失败后 30 分钟重试、按失败次数上限停止、每任务状态持久化 |
| `ai/file_lock.py`、`ai/logging_config.py` | 跨进程互斥、有界诊断日志 |

### 客户端（薄端）

| 模块 | 职责 |
|---|---|
| `__main__.py` | 入口：`python -m client` → `cli.run_interactive()` |
| `cli.py` | 交互主循环：7 个命令路由；普通输入 → 写本地 + push（**只今天**）；启动 full_sync + 历史日整文件校验；后台**持续同步**线程（连接即完整对账，断线自动重连补齐） |
| `terminal.py` | 跨平台终端输入：逐字符、Unicode 感知整字符退格（Windows 控制台事件 / POSIX raw），并处理后台线程通知展示 |
| `identity.py` | 连接凭证与设备身份：读写 `credentials.json`（单一共享 token）；`device_name()` 自报本机名；`make_entry_id(ts)` 以毫秒时间戳为 id（时间戳即标识，不做内容哈希） |
| `atomic_write.py` | 原子文件写入（客户端自带小工具，与服务端各自独立） |
| `render.py` | 日记文件格式本地渲染（标记常量/entry/tombstone/day_header；客户端自带，与服务端 hub/render.py 同款互不引用） |
| `journal.py` | 本地日记写入与对账：**只写“今天”（UTC+8）** `Records/YYYY-MM-DD.md` 原子追加；对账**只对今天**做 `(ts, entry_id)` 时间有序合并；昨天及以前**整文件重放**（云端为准、覆盖本地）；过期未同步、`date < 今天` 的条目直接作废；tombstone 移除（渲染格式用客户端本地 `render.py`） |
| `file_lock.py` | 跨进程互斥（原子写） |
| `sync.py` | 与中枢同步：`push_new` / `send_pending` / `pull` / `longpoll` / `full_sync` / `sync_reports` / `delete_latest` / `status` / `admin_retry` / `admin_set_model`；**push 只发今天**，过期条目丢弃；启动时校验历史日整文件（云端为准覆盖）；断线重连用 `full_sync` 做完整对账 |
| `config.py` / `config.example.yaml` | 本地配置（服务器地址、数据目录）。`config.example.yaml` 是提交的模板；运行时读取 `config.yaml`（已 gitignore），由用户复制并填服务器地址 |

客户端**不密集轮询云端**，且**同步是全自动、无感知的**：

1. 启动时自动一次完整同步（拉取对账 + 冲刷离线队列 + 同步报告）。
2. 运行期间后台线程保持一条**长连接（长轮询）**，服务端有更新即扇出返回并立即应用，超时立即重挂。
3. **服务端离线再上线后，后台线程会自动重新连接并完整对账**，无需手动同步。

断网时本地照常记录并进 `outbox.json` 离线队列，恢复后自动冲刷补齐。

**历史日记（昨天及以前）整文件同步**：客户端启动时对每个 `date < 今天` 的本地日记与云端进行**整文件**
比对，不一致即以云端为准覆盖本地（**不核对时间戳、不做条目级合并**）。历史日为**只读**：客户端从不往
历史日记写入，也不会推送历史日变更；其内容由云端权威保存并可代际承载旧格式（见 §4）。

## 3. 数据模型与记录格式

### 3.1 每条记录（entry）

日记文件中每条记录是一块：

```text
<!-- myrecord-time:<毫秒时间戳> -->
<!-- myrecord-device:<设备名> -->        （可选，便于区分哪台设备写的）
**HH:MM [设备名]:** 正文                （记录的可视头部行）
```

- **entry_id = 写入毫秒时间戳**（epoch ms，字符串）：时间戳即 id。去重、删除都**直接按时间戳比对**：
  同一写入毫秒即同一条，离线多端各自记录、上线合并时按 id（=时间戳）去重；对个人手写使用，同毫秒碰撞
  概率可忽略。也因 id 即时间戳，文件里的 `myrecord-time` 值既作标识、又**自描述**该记录的确切写入时间，可复原。
- **ts**：**毫秒**精度（`int(now.timestamp()*1000)`）。连续快速记录时秒级时间戳会碰撞，毫秒级让每条
  几乎都有唯一 ts：按 `(ts, entry_id)` 排序即等于按写入顺序排序（此排序用于“今天”的合并/渲染/增量拉取；
  历史日整文件为准、不参与条目级排序，见 §4）。
- **时区**：epoch 本身是无时区的绝对时间（UTC）。展示与按天分组**固定按 UTC+8** 换算：`HH:MM` 由 ts
  在 UTC+8 下取分钟，`date`（文件名 `YYYY-MM-DD`）同样按 UTC+8 推导，多端/跨时区一致。
- **tag**：普通记录无标签；仅“引用”等特殊记录带标签（如 `[引用]`）。
- **删除**：写 tombstone 占位（**只有一行，不含正文**），正文入垃圾桶，不做硬删除，防“已删条目复活”。
  墓碑记录**原条目的时间戳 id**，即“这个时间点上有记录且已被删”，可插回原时间位置、更易复原。

```text
<!-- myrecord-tombstone-time:<原时间戳> -->
```

### 3.2 每日日记文件

每天一个 `Records/YYYY-MM-DD.md`：

```text
# YYYY-MM-DD

<summary>
...每日总结正文...
</summary>

---
## 原始记录流

<!-- myrecord-time:... -->
**HH:MM:** 正文
...
```

`<summary>` 区域由服务端 AI 独占写（见 §8.8），原始记录流部分：**只有“今天”由客户端写入**；昨天及以前
由云端权威保存、客户端**只读整文件**（见 §4）。

**只在有记录时生成文件**：服务端只在某**日确有实际记录**（条目/墓碑）时才渲染 `Records/<date>.md`；
当日无记录则**不生成空占位文件**。这样既避免无意义文件污染 `/api/records` 的日期列表，也避免自动化/AI
把它误判为“有内容”（§9.2 约定：缺失文件一律视为 `empty` 无内容）；客户端对无文件的日子显示“还没记录”。

### 3.3 标记解析

解析器识别 `myrecord-time` / `myrecord-device` / `myrecord-tombstone-time` 三种新格式标记。
解析得到的标记注释不混入正文，AI 只读正文文本。

**不兼容旧格式**：历史日记（含旧式 `**HH:MM:**` 无时间戳行、`<!-- agentrecord-record -->` 等旧标记）
不作为“条目”解析、也不被回写或重排——它们以**整个文件**为单元由云端权威保存并原样回传（见 §4），
客户端对历史日记只做整文件覆盖，不需要理解其内部格式。

## 4. 同步与对账协议

> **唯一可写窗口 = “今天”（UTC+8 自然日）。** 客户端只能推送 `date == 今天` 的条目；服务器对
> `date != 今天` 的条目（含过期历史日与异常未来日期）**一律拒绝**。历史日内容为只读、以云端整文件为准，客户端拉取即覆盖本地。

| 端点 | 用途 |
|---|---|
| `POST /api/sync/push` | 推送新条目（`{entries, version}`，**仅今天**；历史日条目被服务端拒绝） |
| `GET /api/sync/pull?version=N` | 拉取“今天”的增量（条目/墓碑，`(ts, entry_id)` 有序） |
| `GET /api/sync/longpoll?version=N` | 长轮询扇出（仅今天的新变化） |
| `GET /api/records` | **哈希清单**：返回每个历史日的 `(date, sha256)`（供客户端按需整文件同步） |
| `GET /api/records/<date>` | **整文件拉取**某天日记（历史日：云端权威、客户端覆盖；仅哈希不同才拉取） |
| `POST /api/entries/delete` | 在线删除“今天”最新一条 |
| `GET /api/status` | 服务端状态 |
| `GET /api/reports` + `/api/reports/<kind>/<name>` | 报告**哈希清单** / 内容（清单列出 `(rel, sha256)`，仅哈希不同才拉取内容） |
| `GET /api/health` | 存活探针（无需鉴权） |
| `POST /api/admin/retry`、`/api/admin/model` | AI 任务重试 / 切换模型 |

鉴权：全部接口需 `Authorization: Bearer <token>` + `X-Device-Id`（客户端自报本机名）。
`store.append_entries` 按 `entry_id` 去重合并，维护全局 `version` 游标作为“今天”的增量边界。

**`version` 的语义（读/写端点不同）**：`version` 是服务端维护的全局单调递增游标
（`state.json`），客户端在本地 `state.json` 保存“已同步到第 N 版”。

- **读端点**（`GET /api/sync/pull`、`GET /api/sync/longpoll`）：`version` 是请求本身的输入，
  请求目的即“返回第 N 版之后的增量”。**缺失/为空时回退到 `0`（全量）**（无法确定增量边界时
  用全量兜底、保证无缺口，语义与写端点一致）；仅当传入了**非数字**的 `version`（如 `version=abc`）
  才返回 400（该值无法解析为合法游标）。对应服务端 `hub/server.py` 的 `_query_version`。
- **写端点**（`POST /api/sync/push`、`POST /api/entries/delete`）：`version` 只是辅助游标，
  主操作（入库 / 删墓碑）不依赖它，它只决定响应里返回哪段增量。非法/缺失时**回退到 `0`（全量）**，
  响应更大但保证无缺口（不遗漏中间条目）。对应 `_write_response_version`。

**今天（`date == 今天`）**：客户端 push 新条目 → 服务端按 `entry_id`（= 毫秒时间戳）去重合并、写后即时
渲染；多端并发追加时按 `(ts, entry_id)` 时间有序；`longpoll`/`pull` 只返回今天的新变化，客户端据此增量补齐。
删除仅作用于今天最新一条（tombstone）。`GET /api/status` 的 `entry_count` / `tombstone_count` 同为
**仅今天**计数：历史日封存进 `Records/*.md` 整文件后即不再计入 `state.json`，故不算入两者。

**历史日（`date < 今天`）**：**整文件同步**，不做条目级合并、不核对时间戳。客户端启动时先取
`GET /api/records` 的**哈希清单**，对每个 `date < 今天` 的本地文件算 SHA-256 比对，**只有哈希不同**才
整文件下载 `GET /api/records/<date>` 覆盖；哈希相同则跳过——避免每次启动对全部历史日做全量拉取与逐字节比对
（否则历史日越多、启动越慢，动辄几十秒）。**清单即权威全集**（`{files:[{date,sha256}]}`），不再保留旧的
纯日期字符串字段（`dates`）——客户端只依赖 `files`，不做向后兼容。服务端对这些文件**原样保存并回传**
（可承载旧格式，见 §3.3），不解析、不重排、不复渲染。

**报告同步同理**：`GET /api/reports` 返回 `{files:[{rel,sha256}]}`（不再保留旧的 `reports` 字符串字段），
客户端只对哈希不同的报告拉取覆盖，未变的报告不再整文件下载。

**本地多余历史文件同步即删除**：对 `date < 今天` 且**云端不存在**的本地 `Records/*.md`（含此前离线写入、
跨零点作废又未推送的日子），客户端同步时按“云端为准”**删除整文件、不留本地副本**。历史日以云端全集为
绝对标准：本地存在的每个历史日文件都必须能在云端拿到同源内容，否则即视为已作废并移除。
**未来日期（`date > 今天`）的本地残留文件**（异常：本地时钟漂移或旧客户端产物）同样**只保护“今天”**，
云端不存在即一并清理，避免异常残留污染对账。

**过期未同步即作废**：客户端在每天开始时（UTC+8）丢弃 `outbox.json` 中 `date < 今天` 的条目，不再推送；
服务端亦拒绝这样的推送作双保险。因此“昨天的未同步记录”不会在第二天被补写进云端。

## 5. 连接凭证与传输加密（强制）

### 5.1 连接凭证（单一共享 token）

- 签发：`python -m server.main token create` 用 `secrets.token_urlsafe(32)`
  生成约 43 个 URL 安全字符的超长随机 token，打印一次后不再可见。重签（覆盖旧 token）会提示二次确认。
- **服务端只存哈希**：`hub/auth.py` 用 `hashlib.scrypt`（加盐、`N=2^14`、常量时间比较）存为
  `scrypt$N$r$p$salt$hash`。数据空间泄露也无法反推明文。
- **单一共享凭证**：不绑定设备；设备由各端自报 `X-Device-Id` 区分。`create` 覆盖旧 token（无多凭证/多设备）。
- **无凭证/凭证错误**：客户端只能本地记录，无法把修改传上服务端或拉取/删除云端数据。
- **爆破防护**：连续鉴权失败 5 次按设备锁定 60 秒，并记日志。

### 5.2 传输加密（强制 TLS，自签直连）

- `python -m server.main run` 未配置 TLS 会**拒绝启动**（禁止明文，返回码 2）。
- `python -m server.main cert` 生成**自签证书（同时具备 CA 能力，有效期 10 年）**及私钥，写入
  `data/tls/server.crt` 与 `server.key`；`--ip`/`--dns`/`--cn` 指定 SAN 覆盖客户端连接地址。
- 客户端 `config.yaml`：`server_url` 为 `https://…`，`verify` 指向复制过来的 `server.crt` 校验收信。
- `ThreadingHTTPServer` 直接把监听 socket 用 `SSLContext` 包裹成直连 HTTPS，无需反向代理。
- 信任锚是**首次分发（TOFU）**：首次可靠地把 `server.crt` 送到客户端并手动指向它，此后每次严格验真。

## 8. 云端 AI 分析设计

### 8.1 总原则：原始记录是唯一事实源

周报 / 月报**只读取各自时间范围内的完整原始记录流**（按日期分隔的 `Records/YYYY-MM-DD.md`），
作为**唯一事实来源**。报告**不读取**每日总结、旧周报、旧月报、引用历史记录或其他任何历史报告，
避免“摘要层层传递”造成信息损失。原始记录流是原始事实，派生的总结/报告不得再作为事实输入。

### 8.2 报告生成流程：单次 Report Agent

每周 / 每月报告由**单次 Report Agent 一次性直接生成完整报告**。其分工为：

- **Agent**：一次性阅读中控提供的按天分块记录流，整理内容，并返回**纯 JSON 对象**：`summary`
  （含 `[n]` 引用编号的报告正文）+ `references`（每个引用编号对应的来源）。
- **中控（程序）**：构造提示词（含任务、引用规则、JSON 输出结构与示例）、拼接记录流（按天分块 +
  行号）、解析返回的 JSON、校验引用合法性、写入头部审计元数据与文末来源表、原子交付报告。
  中控不做 AI 审核。

### 8.3 中控输入：按天分块 + 行号

记录流**按天分组**，每天一个块。**块首行是 `[YYYYMMDD]`**（英文方括号），**块内每行格式为
`行号: 内容`**（英文冒号）。所有块按日期顺序拼接。

具体约定：

- **行号**：一条记录在**其所属日期文件**中的 1-based 行号，定位到该记录的可视头部行（`**HH:MM:**`
  开头的那一行）；引用来源 `R-YYYYMMDD-行号` 中的行号与之完全一致。

输入呈现形如：

```text
[20260816]
1: 今天去了公园，天气很好。
2: 下午和朋友聊天，讨论了项目计划。
[20260817]
1: 早上开会，确定了本周目标。
```

### 8.4 提示词与 Agent 交付：纯 JSON（summary + references）

提示词明确：

- **任务**：基于输入记录生成周报 / 月报的 `summary`，并对 `references` 中的每个编号给出来源。
- **引用规则**：总结正文引用具体信息时，在句子末尾标注引用编号，如 `[1]`、`[2]`（从 1 开始，
  连续编号）；在 `references` 数组中列出每个编号对应的来源。
- **来源格式**（全部英文半角标点）：
  - 单行：`R-YYYYMMDD-行号`，例如 `R-20260816-1`。
  - 多行连续：`R-YYYYMMDD-起始行-结束行`，例如 `R-20260816-2-3`。
- **只引用输入中实际出现的行号，不得编造**；若信息来自连续多行则合并为一个引用，单行只写一个行号。
- 提示词包含**至少一个完整示例**（输入片段 + 输出 JSON），展示单行与多行引用的写法。

Agent 必须返回**纯 JSON 对象**（不要任何额外文字或 Markdown 代码围栏），结构如下：

```json
{
  "summary": "包含引用编号的总结文本",
  "references": [
    {"id": 1, "source": "R-20260816-1"},
    {"id": 2, "source": "R-20260816-2-3"}
  ]
}
```

`summary` 是字符串（内文可用 Markdown 排版，可含 `[1]`、`[2]` 等标记）；`references` 数组按 `id`
升序排列。

### 8.5 输出解析与引用校验（确定性，无 AI 审核）

- 程序用 JSON 解析 `summary` 与 `references`；若模型返回被代码围栏包裹，先去除首尾 ``` 标记再解析。
- 解析后逐一校验每个 `reference`（中控确定性校验，不调模型）：
  1. **格式**：符合 `R-YYYYMMDD-行号` 或 `R-YYYYMMDD-起始行-结束行`。
  2. **日期**：该 `YYYYMMDD` 属于本周期范围。
  3. **行号范围**：`起始 ≤ 结束`，且不超过该日期块的最大行号。
- **无效引用直接丢弃**（记录日志），不重试。
- 若整个响应不是合法 JSON、`summary` 为空或不是文本，本次报告生成失败。

### 8.6 来源表（中控生成）

来源表由中控根据**校验后的 `references`** 生成（不额外调模型），例如：

```text
## 来源
[1] R-20260816-1
[2] R-20260816-2-3
```

- **Agent 不参与**来源表的排版与写入；它只交付 `references` 数据。
- 来源表只列出模型交付且通过 §8.5 校验的引用。
- **每行来源末尾补两个空格**（Markdown 硬换行，与 §8.8 头部元数据行一致），否则 `[1] …` / `[2] …` 会被渲染
  挤成一段而不换行。

### 8.7 报告文件布局与统一生成

- 手动与自动共用**相同的生成流程**，调用同一个入口，报告文件走统一路径。
- 报告文件路径（无 `_manual` / `_auto` 后缀）：

```text
AnalysisReports/Weekly/YYYY-MM-DD_to_YYYY-MM-DD.md
AnalysisReports/Monthly/YYYY-MM.md
```

- **手动重新生成时直接覆盖**该时间范围对应的原有报告文件（同路径原子替换）。
- 自动任务检测“该周期报告是否已生成”时，同样检查**这个唯一路径**是否存在。

### 8.8 报告头部审计元数据

报告头部保留审计元数据：

```text
# <报告名>

> 生成时间：YYYY-MM-DD HH:MM
> 使用模型：<model>
> 生成耗时：…
> Token 用量：…（输入/输出/缓存命中/缓存未命中）
> 原始日记范围：YYYY-MM-DD 至 YYYY-MM-DD
> 分析运行：<run_id>
```

这些元数据来自中控的确定性统计（Timer、UsageAccumulator 累计的真实调用遥测），**不来自模型**。

### 8.9 每日总结（独立速览；报告不依赖它）

每日总结由服务端把一天内容的要点写入该日日记顶部 `<summary>` 区域，仅作当日速览。
它有**独立的确定性格式校验 + 有界格式重试**（非 AI 审核）：拒绝 JSON / 代码围栏 / 包装标签 /
正文内标题；不合格时附“中控格式修正”再试（`daily_summary_retry_limit`，默认 2）；
防陈旧写入（写入前比对日记内容哈希，生成期间被改则不写）。

报告不读取每日总结（见 §8.1）：每日总结不是周/月报的事实输入，二者相互解耦。

## 9. 自动化任务（简单重试机制）

服务端有一个后台调度线程，只做两件事：**每 15 分钟检测一次缺失**，并**执行所有到期任务**。三种任务
（昨日日记总结、上一完整自然周周报、上一完整自然月月报）**互相独立、互不依赖**——报告只读本周期原始
记录流（§8），不读总结或其它报告，因此**无顺序要求**，检测到即可各自独立生成。

### 9.1 缺失检测（每 15 分钟）

判定「任务是否存在」只依据两件事：

- **产物文件是否存在**：周/月报 = 该周期报告文件是否已生成；日总结 = 昨日日记的 `<summary>` 是否已写。
- **对比当前时间**：周期目标由当前时间推出（昨日、上一完整自然周 = 周一起 7 天、上一完整自然月）。

新发现缺失 → 该任务**立即到期**开始首次生成；周期内无任何记录的任务不视为缺失（无事可做）。

### 9.2 任务状态（严格以文件为准）

每次扫描按产物文件把任务归为三类状态之一（**绝不把「无内容」误标为「已生成」**）：

- **空置（`empty`）**：该周期**没有任何日记内容**，无事可做。判定以**文件存在性**为准：按 §3.2，
  无记录日不再生成文件，因此**缺失文件即 `empty`**（昨日无日记文件 / 周月周期内无日记文件）。
  服务端启动时会清除历史部署遗留的 `（当日暂无记录）` 空占位文件（见 automation 的启动清理），
  故文件存在即代表有记录、不存在即无内容。
- **已生成（`ok`）**：产物文件已存在（昨日总结已写非占位正文 / 周月报告文件已生成）。
- **待生成（`missing` → `pending` / `running`）**：有内容但无产物，需要（重新）生成。

`pending`（待生成）与 `running`（正在生成）的差别仅在于**是否已发起模型请求**：`pending` 是
检测到的「到期、等待执行」，`_process_due` 每 1 分钟一次，一旦执行（且模型可用）即在同一调度周期内
置为 `running` 并发起请求——因此 `pending` 通常只在检测到缺失与真正开始生成之间**短暂存在**；
若模型未配置则直接落到 `unconfigured` 而不生成。

`/status` 展示的逐任务状态：`ok` 已生成 / `empty` 无内容（该周期无记录）/ `pending` 待生成 /
`running` 正在生成 / `failed` 失败（待重试）/ `blocked` 失败（已停止自动重试，需手动重试）/ `unconfigured` 未配置（无AI）。
失败与未配置状态会携带 `error`（原因）；`failed` 另带 `next_retry_at`（下次重试时间）。
`running` 会在生成期间落盘，使 `/status` 能在耗时生成（尤其周/月报）时如实显示「正在生成」。

### 9.3 失败重试（不区分失败类型）

- **不区分任何失败类型**（网络 / 内容 / 视作不可重试的配置错误除外）：生成失败即记一次失败，**立刻开始计时**，
  **30 分钟后自动重试**。
- **配置错误不算失败**：模型未配置 / 活动模型缺 `api_key`（这类问题重试无法自愈，改配置即重启）→ 记
  `unconfigured`（未配置无AI），不进入失败重试，也不排队。
- 每个任务有**各自的重试次数参数**（`daily_summary_retry_limit` / `weekly_report_retry_limit` /
  `monthly_report_retry_limit`，**默认 2**，即首次后再重试 2 次，共执行 3 次）。达上限后**停止自动重试**。
- 每次生成后保存该任务状态：`status`（见 9.2）、`error`（失败/未配置原因）、`attempts`（已执行次数）、
  `next_retry_at`（下次重试时间；达上限/已完成/未配置后为空）、`started_at`（进入 `running` 的时间，用于崩溃恢复）。

### 9.4 手动 /retry

`/retry` 命令**直接重试全部失败任务**（重置各自计数、立即再试一轮），不按顺序、不做依赖约束。

### 9.5 状态持久化

`.automation-state.json` 保存每次检测时间与每个任务的状态（上文 9.2 字段），供 `/status` 查看。
周期目标判定：周 = 周一起算的完整 7 天；月 = 自然月；报告只对该范围原始记录流生成（§8.7）。

## 10. 部署与备份

### 10.1 运行与部署

- 服务端：`pip install -r server/requirements.txt`，`python -m server.main run`（强制 TLS）。
- 客户端：`python -m client`（启动自动同步 + 长连接）。
- 服务端子命令详见 §2 模块表；`cert` 生成自签 TLS；`deploy` 一键安装 systemd 单元
  （仅 `myrecord-server.service`，自动带出解释器与工程根，证书缺失时先自动生成），并立即启动
  服务；若之前部署过备份单元/定时器，`deploy` 不再涉及——**每周自动备份已由服务端内置调度触发**
  （见 §10.4）。

### 10.2 数据空间是唯一事实源

服务端数据空间 `server/data/` 是唯一权威事实源（`state.json`、`Records/`、`Trash/`、
`AnalysisReports/`、`Log/`、`tls/`），客户端本地只是对账副本。因此备份针对**整个
数据空间做整体快照**，不做逐条增量、不做差分，备份后状态与备份时刻等价。**不提供一键整体
恢复覆盖**：数据出现问题往往不是整体覆盖所能解决的，需人工逐条核对，因此只做按时备份。

### 10.3 备份

- `server/deploy/backup.sh [备份目录] [保留份数]` 将整个数据空间打成**单个 gzip tar 快照**。
- 数据目录从 `server/config.yaml` 的 `data_dir` 读取（支持相对/绝对路径）；脚本自定位于其所在
  `server/` 工程根，不依赖调用时的当前目录。
- 默认备份目录为 `backups/`（`server/` 下），默认保留最近 **7 份**；快照名带时间戳
  （`MyRecord-data-YYYYMMDD-HHMMSS.tar.gz`），按时间排序后自动清理超量旧快照。
- 快照为**全量**：一次备份涵盖数据空间全部内容（`state.json`、`Records/`、`Trash/`、
  `AnalysisReports/`、`Log/`、`tls/` 证书与私钥）；**不含模型密钥**——模型密钥只在
  `server/config.yaml`，不入数据空间，故不随备份走。

### 10.4 自动备份（单服务内置调度）

- 备份由**服务端内置后台调度**触发：服务运行期间调度线程定期（默认每 60 秒）检查是否距上次
  成功备份满 **7 天**，到期即作为**子进程**执行 `server/deploy/backup.sh`，把整个数据空间打成
  单个 gzip tar 快照并保留最近 **7 份**。
- **只部署一个 systemd 单元**（`myrecord-server.service`）：不额外安装 `myrecord-backup.service` /
  `myrecord-backup.timer`。`backup.sh` 仍是独立脚本，可手动运行或交由外部 cron 定时，两者共存。
- **状态持久化**：上次成功备份时间写在 `data_dir/.backup-state.json`；备份失败不更新该时间，
  下次检查仍视为「到期」而自动重试。服务端停止期间（如整机下班、未开机自启）错过的备份，会在
  下次启动后立即补跑（等效于 timer 的 `Persistent=true` 补跑语义）。
- 备份作为**子进程**执行，与主进程隔离：失败/异常只记日志、不中断服务；快照内容与备份时刻的
  数据空间状态等价（见 §10.2）。
- 手动/临时备份：`server/deploy/backup.sh [备份目录] [保留份数]`（默认 `server/backups/`、保留
  最近 7 份）；也可用 `crontab -e` 每日调用 `backup.sh` 自行定时。
- **主服务不 `enable`（不开机自启）**：部署出错后重启不会自动拉起损坏服务，便于人工介入排查；因此内置
  备份也只随服务启动而生效（服务不运行则不备份、也无法补跑）。
