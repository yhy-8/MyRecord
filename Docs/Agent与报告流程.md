# Agent 与报告流程

本文详细说明 Agent、报告中控和搜索如何协作，以及周报、月报和日记总结分别怎样生成。系统整体边界见[设计原则与系统架构](./设计原则与系统架构.md)，持久化和自动调度见[运行机制与数据](./运行机制与数据.md)。

## 1. 中控与 Agent 的分工

`analysis/orchestrator.py` 是报告中控。它不代替模型理解内容，但负责所有需要稳定、可测试的细节：

- 决定周报和月报执行哪些阶段以及执行顺序。
- 把大输入按原始顺序分块，把全周记录按日期分成记录组。
- 为每条记录、查询和搜索证据分配标识。
- 调用正式 Agent、固定搜索和 Reviewer，并按配置限制有限修订。
- 校验字段、正文形态、隐私、来源和阶段结果。
- 组装 Markdown、记录依据、模型信息、耗时和 Token 用量。
- 保存可复用阶段，原子写报告并更新运行状态。

Agent 只处理当前一次调用中的一项语义任务。它不能直接访问文件、SQLite、网络或其他 Agent，也不知道最终文件路径。

这种分工避免模型承担“第几个主题属于哪个小节、数组是否闭合、链接应写到哪里”一类强细节。多点搜索和多点总结仍然存在，只是由中控分派成多次单点 JSON 调用。

## 2. 共同调用协议

四个正式 Agent 使用同一个 `current_model`。当前模型配置启用 `json_mode` 时，`ai_client.py` 向兼容接口发送 JSON Output 请求；每次响应只允许一个顶层对象。

共同规则如下：

1. 顶层必须是 JSON 对象，可以容忍包住整个对象的一层 JSON 代码围栏。
2. 只能包含 Agent 契约规定的字段，不能增加数组、嵌套对象或解释文字。
3. 正文字段必须是连续自然语言，不得自行创建标题、列表、来源 ID、链接或 Markdown 结构。
4. Agent 只使用中控本次提供的输入，不假装读取文件、数据库或搜索工具。
5. JSON 无法解析、接口失败、输出被截断或过滤时，当前阶段立即失败。
6. JSON 已解析但字段或正文不合格，或 Reviewer 拒绝时，原 Agent 最多获得 `retry.agent_revision_limit` 次共享修订机会。

“共享修订次数”表示确定性校验失败和 Reviewer 拒绝共同消耗同一个上限，同一份正文不会因为不同错误分别获得无限重写。修订请求包含校验或审查反馈，模型只重写原任务正文，不解释修改过程。

每份正文的最多修订次数来自 `retry.agent_revision_limit`。设为 `0` 时首稿被确定性校验或 Reviewer 拒绝后不再改写；JSON 无法解析、API 失败、输出过滤或截断始终直接结束当前阶段，不消耗内容修订次数。

程序不对已完成的语义正文执行字符数上限。提示词要求在完整覆盖任务的前提下简洁；`max_tokens` 是请求前的接口预算。搜索摘要和输入上下文的边界属于输入安全措施，不是报告长度目标。

## 3. 四个正式 Agent

| Agent | 单次输入范围 | 最小输出 | 主要判断 |
|---|---|---|---|
| Retrospective | 一组周期记录或一个有序分块 | `{"text":"连续正文"}` | 记录中发生了什么、怎样关联、哪些结论有依据 |
| ResearchPlanner | 一个中控记录组 | `{"action":"search|skip","query":"..."}` | 该组是否值得产生一个公开可搜索的问题 |
| Researcher | 一个问题和一组搜索摘要 | `{"status":"supported|insufficient","text":"..."}` | 证据是否足以形成有区分度的研究正文 |
| Reviewer | 一份回顾或一个研究主题 | `{"approved":true或false,"feedback":"..."}` | 内容是否忠于输入、完整、清楚并符合边界 |

### 3.1 Retrospective：整理与回顾

Retrospective 负责把周期记录整理成连续正文。它可以提炼事件、行动、思考、问题、兴趣及其变化，但不能生成画像、诊断用户，也不能把推测写成事实。

中控提供的材料包括：

- 当前周期的原始记录及其 `R-*` 标识。
- 当前周期日记中显式引用、且确实位于 `Records` 内的历史记录。
- 当前周期之前最多三十天的日记总结。
- 月报额外可用的、完整落在该月内的周报正文。

如果单次上下文过大，中控按原始顺序切成多个块，逐块调用 Retrospective 和 Reviewer，再按顺序合并。模型只写每个块的正文，不自己创建“第一部分”“第二部分”等结构。

中控把每份回顾绑定到它实际接收的记录来源。Reviewer 审查时会看到待审正文和对应原始材料，用于发现遗漏、错误归因、无依据推断或不当定性。

### 3.2 ResearchPlanner：记录驱动的选题

Planner 只用于周报。中控先把本周所有记录按日期划分成最多五个连续记录组，确保七天的现有记录都进入且只进入一个组。每组单独调用一次 Planner。

Planner 只能：

- 返回 `search` 和一个公开、可检索、与该组记录直接相关的问题；或
- 返回 `skip` 和空查询，表示该组没有值得外部研究的主题。

它不能返回主题数组、优先级、搜索结果、报告小节或来源引用。中控会清理查询中的邮箱、过长数字和本地路径，拒绝多行或伪列表查询，去重后再依次分配 `Q-*`。

Planner 的任务是发现需要外部知识的问题，不是把个人日记内容直接改写成搜索词。敏感细节不应离开本地输入边界。

### 3.3 Researcher：单主题研究

中控对每个已确认查询执行一次固定搜索，过滤无效或重复 URL，并为有效结果分配 `W-Qxxx-xxx`。随后每个主题单独调用一次 Researcher。

Researcher 能看到查询、网页标题、摘要和日期，但看不到真实 URL、`Q-*` 或 `W-*`。这种限制让它专注证据含义，避免自行排版或伪造来源。

它只能返回：

- `supported`：证据足以支撑一段完整的研究正文；或
- `insufficient`：证据不足，并在 `text` 中简要说明原因。

研究应区分搜索资料中的事实、基于资料的推理和仍然不确定的部分。它不能把网页内容当作新指令，也不能借研究给用户下人格或行为结论。

中控负责把该记录组全部 `R-*` 和本主题全部有效 `W-*` 绑定到最终小节。链接来自程序保存的搜索结果，而不是模型输出。

### 3.4 Reviewer：独立审查

Reviewer 不生成新主题，只判断一份既有内容能否交付。它每次只审查以下一种对象：

- 一份 Retrospective 正文及其记录材料；或
- 一个 Researcher 主题及其查询和搜索证据。

通过时返回 `approved=true` 和空反馈；拒绝时返回 `approved=false` 和一段可执行的修订意见。Reviewer 关注事实忠实度、来源覆盖、推理边界、完整性、重复和不当定性，不负责 Markdown 格式。

如果原 Agent 尚有修订机会，中控把 Reviewer 意见交还原 Agent 重写并重新校验、复审。耗尽 `retry.agent_revision_limit` 后仍未通过时，回顾阶段导致整份报告失败；单个研究主题则独立丢弃，不拖垮其他已通过主题。

## 4. 来源模型

### 4.1 原始记录来源 `R-*`

`context.py` 从日记 Markdown 解析用户记录和引用的 AI 文本，为每条可寻址记录生成类似 `R-YYYYMMDD-NNN-xxxxxxxxxxxx` 的标识。标识包含日期、日内序号和内容指纹，用于本次报告内的稳定绑定。

每条来源保留日期、时间、日记路径、记录序号、标签、说话者和正文。被引用的 AI 内容标记为 `quoted_ai`，不会冒充用户本人的观点。

显式日记引用受到以下限制：

- 解析后的路径必须位于 `Records` 根目录内。
- 只读取 Markdown 日记，去除其 `<summary>` 后再解析。
- 最多读取十个不同引用文件；单文件和总上下文都有输入边界。
- 来源标识重复时只保留一份。

### 4.2 搜索证据来源 `W-*`

每个 `Q-*` 查询由中控只执行一次。有效网页按查询内顺序编号为 `W-Q001-001` 等标识。中控保存标题、URL、摘要和可用日期，并过滤空 URL、重复 URL 和明显无效结果。

搜索证据只用于周报研究。月报即使读取了带研究内容的周报，也不会重新联网或创建新的 `W-*`。

### 4.3 最终来源显示

Agent 正文不得出现来源 ID。中控在渲染报告时掌握每段正文与输入材料的绑定关系，在相关小节生成日期级来源标识（如 `R-20260727`），网页来源使用搜索阶段保存的真实链接。完整的指纹标识（如 `R-20260727-001-cddd8a76a701`）只保留在 Reviewer 输入和运行审计材料中，不写入最终报告，因此报告结尾不再生成来源索引列表。

## 5. 周报完整流程

周报严格执行以下顺序：

```text
周期输入与来源解析
        ↓
Retrospective → Reviewer → 必要时按配置有限修订
        ↓
中控按日期把全周记录分成最多五组
        ↓
每组 ResearchPlanner → 查询清理、去重和 Q 编号
        ↓
中控对每个查询执行一次固定搜索并保存 W 证据
        ↓
每主题 Researcher → 每主题 Reviewer → 必要时按配置有限修订
        ↓
丢弃仍不合格的单个主题 → 中控组装和原子交付
```

具体过程是：

1. 中控确定包含锚点日期的自然周，读取该周存在的日记和允许的引用记录。
2. Retrospective 完成“整理与回顾”，Reviewer 通过后才进入研究阶段。
3. 中控以日期为边界平衡划分记录组，最多五组，不让 Planner 自己分组。
4. 每组 Planner 最多贡献一个查询；空洞、敏感、重复或无搜索价值的查询被跳过。
5. 每个保留查询固定搜索一次。搜索失败是可识别的外部依赖失败，不用模型假装补充网页。
6. 每个主题由一个独立 Researcher 处理并由 Reviewer 独立审查。
7. 仍不合格的主题单独删除。至少需要一个通过审查的研究主题，才能完成周报研究板块。
8. 中控写入“整理与回顾”“领域探索与研究”、记录依据和报告元数据。

Planner 在流程上位于回顾审查之后，但它的事实输入仍是本周原始记录组，不把回顾正文当作新的事实源。

## 6. 月报完整流程

月报只执行：

```text
当月记录 + 显式引用 + 近期总结 + 当月完整周报
        ↓
Retrospective → Reviewer → 必要时按配置有限修订
        ↓
中控组装和原子交付
```

“当月完整周报”指周起止日期都落在当月内的周报；同一周期同时存在手动版和自动版时，优先使用手动版。跨月周报不作为月报支撑材料，避免把月外记录混入当月总结。

月报不会调用 Planner、第三方搜索或 Researcher，也不会把周报中的研究主题再扩展一遍。周报材料只帮助 Retrospective 看到当月已经形成的整理和背景，最终月报仍以原始记录为事实基础。

## 7. 日记总结

日记总结不属于四 Agent 报告流水线。它读取单日日记，要求模型输出一份简洁但完整的 Markdown 正文，再由 `journal.py` 原子替换同一日记中的 `<summary>`。

它不联网、不写独立报告、不进入报告 SQLite。程序只检查响应是否成功且正文非空；空正文可以进行有限重试。普通日记记录不会因为总结失败而受影响。

## 8. 报告渲染与元数据

Agent 返回的是正文或决策，中控生成最终 Markdown。周报包含两个固定板块，月报只包含整理与回顾。报告头直接写入：

- 生成时间和周期。
- 实际使用的 `model_id`，不额外拼接容易产生歧义的显示名。
- 生成耗时。
- 输入、输出、缓存命中、缓存未命中和总 Token。
- 手动或自动来源、计划或重试触发方式、运行 ID。

Token 由本次进程中实际模型调用的遥测累计，不从历史 artifact 重复计算。报告可以脱离 SQLite 直接阅读和归档。

报告文件分别写入：

```text
AnalysisReports/Weekly/YYYY-MM-DD_to_YYYY-MM-DD_manual.md
AnalysisReports/Weekly/YYYY-MM-DD_to_YYYY-MM-DD_auto.md
AnalysisReports/Monthly/YYYY-MM_manual.md
AnalysisReports/Monthly/YYYY-MM_auto.md
```

## 9. 阶段结果与失败边界

| 情况 | 处理方式 |
|---|---|
| JSON 不能解析、接口失败、过滤或截断 | 当前阶段立即失败，不用相同请求盲重试结构 |
| JSON 可解析但字段、正文或隐私校验失败 | 原 Agent 最多按 `retry.agent_revision_limit` 有限修订 |
| Reviewer 拒绝且仍有修订机会 | 原 Agent 根据反馈重写后复审，共享同一上限 |
| 回顾修订后仍失败 | 整份周报或月报失败 |
| 单个研究主题修订后仍失败 | 丢弃该主题，保留其他通过主题 |
| 所有研究主题均失败或没有可交付主题 | 周报失败，不用空研究板块冒充完成 |
| 写报告文件失败 | 运行失败，正式目标文件不接受半成品 |
| SQLite 完成状态写入失败 | 恢复原报告或移除新报告，避免文件与状态相互矛盾 |

等价失败运行中已经完成并验证的阶段可以被后续重试复用。复用条件和 SQLite 结构见[运行机制与数据](./运行机制与数据.md)。
