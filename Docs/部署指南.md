# MyRecord 部署指南

本文是简明的**操作步骤**。代码结构见 [代码结构.md](./代码结构.md)，安全/加密/日志/AI 的
权威设计见 [设计基线.md](./设计基线.md)。两端架构：服务端是数据中枢
+ 云端 AI；客户端是薄记录端。二者**严格分离、各自独立部署**：只有极少
代码重合（原子写入、日记文件格式）各自内置一份，互不导入、不共用 `common/`。部署默认使用
**自签证书 TLS 直连**（无需反向代理）。

> 两个强制前提：① **加密是必须的**（服务端未配置 TLS 会拒绝启动）；② **修改/同步日志必须携带
> 服务端签发的连接凭证**（无凭证只能本地记录）。

---

## 1. 服务端部署（Linux + systemd，HTTPS 直连）

前置：Python ≥ 3.10（系统默认 `python3` 即可，**无需手动建虚拟环境**——`deploy` 会为服务运行时
单独创建 `server/.venv` 并装依赖）。

**一键 `deploy` 是主要方法**，它自动完成虚拟环境、依赖、自签证书、链接凭证与 systemd 单元的
全部装盘与启动（**无需预先 pip install 到默认/系统 Python**）：

```bash
cd <server工程根>                      # 含 server/ 子目录的独立工程根（从这一层运行 python -m server.main）
cp server/config.example.yaml server/config.yaml    # 生成运行配置，再填入模型 api_key
sudo python -m server.main deploy      # 一键部署：自建 venv + 装依赖 + cert + token + 写入并启动单元
sudo journalctl -u myrecord-server -n 30   # 确认日志
```

> `config.example.yaml` 是提交的**配置模板**（api_key 留空）；运行时读取的是 `config.yaml`
> （含 api_key，已 gitignore，不入版本库），请务必复制模板后**填入你的模型密钥**。

> `deploy` 会自动完成以下步骤后写入并启动 **1 个单元**（服务端单元 `myrecord-server.service`；
> 每周自动备份由服务端内置调度触发，不再安装独立的备份单元/定时器）：
> ① **创建虚拟环境** `server/.venv`（Python 原生 venv，缺失才创建），并把 `server/requirements.txt`
>    装进该 venv——服务运行时用 `server/.venv/bin/python`，与当前解释器隔离；② 缺失则生成自签证书；
> ③ 尚无有效凭证时自动签发链接凭证（token，打印一次，不会覆盖旧 token）；④ 按当前包实际位置渲染单元
>    （`ExecStart` 用 `server/.venv/bin/python`，不写死 `server/`，因此 `server/` 可改名）。
> 然后执行 `systemctl daemon-reload` 并 `systemctl start` 主服务。
> **主服务只 `start`、不 `enable`**（不做开机自启动，部署出错后重启不会自动拉起损坏服务、
> 便于人工介入排查；如需开机自启请自行 `systemctl enable myrecord-server`）。
> **每周自动备份已内置**：服务运行期间距上次成功备份满 7 天即作为子进程执行 `backup.sh`（见 §4）。
>
> **重新部署（同名服务）**：再次运行 `sudo python -m server.main deploy` 即可。若检测到同名
> 服务单元已存在（前一进程仍在运行），`deploy` 会**先 `systemctl stop` 关停原服务**、**覆盖写入最新单元**
> 后 `daemon-reload` 并**重新 `start`**，**仍不 `enable` 开机自启**。无需先手动删旧单元或手动停服务；
> 首次部署时单元尚不存在，`deploy` 会跳过 `stop`，直接写入并启动。
>
> **部署完成摘要**：`deploy` 结束会打印「部署完成」标题的摘要块，把六方面状态一次说明：
> **虚拟环境**（服务端用 `server/.venv/bin/python` 运行，已切到虚拟环境）、**自签证书**（新生成/已存在）、
> **链接凭证**（新签发 token 或已存在跳过）、**API 配置**（活动模型 api_key 是否已填、AI 可用与否）、
> **服务部署**（单元已写入并启动、不启用开机自启）、**数据备份**（每周自动，见 §4）。若缺 `config.yaml`
> 或 api_key 为空，摘要会给出下一步提示。
>
> **模型 API Key 仍需人工填**：`deploy` 不写入 `config.yaml` 的 api_key。把 `server/config.yaml`
> 里的 api_key 填好后，**只需 `systemctl restart myrecord-server` 即可生效，无需重新部署**。若 `deploy`
> 时还没有 `config.yaml`，服务会以默认配置运行（无 AI 能力）并打印提醒。
>
> **无需预先 pip install**：`deploy` 具备自举能力——若当前解释器不在 `server/.venv` 内，它先用标准库
> `venv` 创建 `server/.venv`，再用 `server/.venv/bin/python` 重新执行自身；依赖（yaml / requests /
> cryptography）一律装进该 venv，**不污染默认/系统 Python**。只需服务器 Python ≥ 3.10 且能联网
> 安装依赖即可，无需先在默认环境手动 `pip install`。
> 若需把服务端公网/局域网 IP 写进证书 SAN（客户端严格校验收信用），可在 `deploy` 之前执行
> `python -m server.main cert --ip 服务端公网IP --ip 127.0.0.1`；`deploy` 检测到证书已存在会跳过生成。

（可选）不打算用 systemd 常驻时，可先前台启动验证（临时跑，Ctrl-C 退出；TLS 未配置会拒绝启动）：

```bash
python -m server.main run
```

服务端证书路径不写入 `config.yaml`：`cert` 统一生成到 `./data/tls/server.crt/.key`，
`run` 固定从该处读取并**强制 TLS**，证书缺失时拒绝启动（提示先执行 `cert`）。

## 2. 签发链接凭证（单一共享 token）

凭证是**唯一共享 token**，不绑定设备：只要你持有它，任意客户端都能连上同步。签发会
**覆盖并删除旧 token**。

```bash
python -m server.main token create
# 输出：token: <一长串随机令牌>   ← 复制保存（服务端只存它的哈希）
# 再次执行会提示覆盖确认（输入 yes）；旧 token 立即失效。
```

把 token 写入客户端 `client/credentials.json`（格式见样板 `client/credentials.example.json`）：

```json
{
  "token": "<将说明文字替换成服务端签发的 token>"
}
```

凭证管理：

```bash
python -m server.main token list      # 查看当前是否已配置有效凭证（含生成时间）
python -m server.main token create    # 重新签发（覆盖旧 token，需输入 yes 二次确认）
```

凭证是**连接许可**：客户端所有同步与修改（推送、在线删除、拉取、状态、报告、AI 管理）都需携带
`Bearer <token>`；无凭证或凭证错误时只能本地记录，无法把修改传上服务端或拉取/删除云端数据。

⚠️ `credentials.json` 是密钥，勿提交进仓库（已 gitignore）；`credentials.example.json` 是样板可提交。

## 3. 客户端部署

```bash
cd <client工程根>
pip install -r client/requirements.txt
cp client/config.example.yaml client/config.yaml   # 用模板生成运行配置,再填入服务端地址
python -m client
```

编辑 `client/config.yaml`（由 `config.example.yaml` 复制而来）：

```yaml
client:
  server_url: "https://服务端IP:8765"   # 启用 TLS 后必为 https
  verify: ""                            # 默认=不校验收信（省事，自签直连；仍加密，但不验服务器身份）
```

> **`verify` 校验收信**：留空 `""` 为**默认**（关闭证书校验——自签直连省事，连接仍是 HTTPS 加密，但不验证服务器身份，有中间人风险）。
> 要**严格校验收信**只需两步：① 把服务端生成的 `server.crt` 拷到客户端；② 把这行改为 `verify: "./server.crt"`。此后每次连接严格验真，建议正式使用采用。

无 token 或离线时客户端也照常本地记录，上线后自动同步。

## 4. 数据备份

数据空间 `server/data/` 是唯一事实源，定期备份：

```bash
server/deploy/backup.sh [备份目录] [保留份数]   # 默认 backups/，保留最近 7 份
crontab -e                                        # 建议每日定时执行 backup.sh
```

> 备份机制详见 [设计基线.md](./设计基线.md) §10。**自动备份由服务端内置调度触发**：服务运行期间，
> 距上次成功备份满 7 天（或从未备份）即作为子进程执行 `backup.sh`（备份到 `server/backups/`，保留
> 最近 7 份）；服务停止期间错过的备份会在下次启动后补跑。因此**无需单独的备份 systemd 单元或定时器**。
> 上面的 `backup.sh` / `crontab` 用于手动/临时备份，二者可共存。

---

## 5. 部署后自检清单

1. `systemctl status myrecord-server` 为 active；
2. `python -m server.main token create` 完成且 token 已写入各客户端 `credentials.json`；
3. 客户端 `python -m client` 能启动、完成首次同步、写入一条记录能即时到达服务端 `data/Records/`；
4. 服务端已填模型密钥，自动任务能调度；
5. 全程 HTTPS（自签证书直连）已生效；
6. 服务启动后会自动做首次备份（`server/backups/` 内出现 `MyRecord-data-*.tar.gz` 快照）。
